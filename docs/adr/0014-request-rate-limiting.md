# ADR 0014 — Request Rate Limiting

**Status:** Accepted
**Date:** 2026-08-27 (the mechanism was decided on 2026-08-26; the numbers below are the ones the production-mode rehearsal measured the next day, and they are not the ones this ADR was first written with). **Amended 2026-08-29** — the shared bucket this ADR named as the follow-up is now the implementation; the note at the end of this file is where that is recorded, and the body above it is left as it was written so the sequencing stays readable.

## Context

Until this release the API had no rate limiting at all, and the project knew it precisely rather than vaguely: `synthetic/load/reliability.py` fired sixty rapid authenticated requests, recorded sixty `200`s and no `X-RateLimit-*` header, and reported the result as an advisory check so that the gap was evidence instead of folklore. CLAUDE.md's remaining-Phase-3 list carried the same item as product-track (c) — "either per-tenant limits against the tenant-config row or an ADR that records the omission deliberately". This ADR is the first half of that choice.

What changes the calculus is that the service is about to be reachable from the public internet (ADR 0013). On the Compose stack the only callers are the developer, the browser journeys and the load harnesses; on the deployed host, `https://<PUBLIC_APP_HOST>` is a public name in front of a two-worker API sharing two vCPUs with a database, a pooler, an IdP and a ranker, and every authenticated `GET /users/{id}/recommendations` costs, in order: a pooled Postgres connection and a `SET LOCAL app.tenant_id`, a tenant-registry `SELECT`, a state read, an item-item retrieval, a batched Feast/Redis online read across up to 500 candidates, a LightGBM predict in the sidecar, and a durable `recommendation_audits` `INSERT` before the response is acknowledged. That is a request whose cost is measured in real database and CPU work, not in bytes served, and non-negotiable #4 puts a p99 SLO on it. One caller in a `for` loop — a mis-written client, a demo left open in a tab with a broken retry, a crawler that found the domain — can consume the whole budget while every other tenant waits behind it.

Three facts about this system constrain what a limiter can key on:

- **The tenant is derived from the verified token issuer, never from a claim the client controls** (ADR 0007). That derivation already exists in `src/auth/middleware.py` and produces a `RequestPrincipal(tenant_id, user_id, …)` before any handler runs. A limiter keyed on it inherits the same forge-resistance for free.
- **Every request arrives from a proxy.** Behind the Caddy edge and Compose's bridge network, `scope["client"]` is the proxy, not the caller. An address-keyed limiter would either treat the entire deployment as one caller or make `--forwarded-allow-ips` and a spoofable `X-Forwarded-For` load-bearing for a security decision. This project has deliberately kept client-supplied headers out of every security decision so far; a limiter is a poor place to start.
- **The synthetic-load harnesses authenticate as a single identity.** The `demo` realm has exactly one user and exactly one client with a direct grant, so k6 at 55 arrivals/second (`smoke`) and 600/second (`nightly`), `synthetic/load/pages.js`, the tenant-isolation canaries and `reliability.py` are all, to a per-subject limiter, the same caller. Any per-subject limit small enough to be worth having is thousands of times below what the SLO gate offers.

A fourth fact constrains what the *number* can mean rather than what the key can be. The API is not one process: `infra/api/entrypoint.sh` starts uvicorn with `${API_WORKERS:-4}` workers, both Compose `api-load` definitions run four, and the deployed host runs two (`API_WORKERS=2` in `infra/deploy/production.env.example`, sized for a 2-vCPU machine). Nothing on the request path is shared between those processes, so any limiter that lives in one of them is approximate before it performs any arithmetic at all — and, as the measurement below shows, the approximation does not run in the generous direction for a single client. That is a property to state up front and keep stating, not one to be discovered by a client whose backoff logic quietly stopped working.

It is worth naming what this limiter is *not* for, because that is what makes the alternatives comparable. It is not a billing quota — nothing here is metered, and a worker restart forgives whatever a caller had spent. It is not a defence against a volumetric attack — an unauthenticated flood never reaches it, because the auth middleware answers `401` first, and a real flood is an edge problem. What it bounds is the sustained cost a single *authenticated* caller can impose on a shared ranking path, which is the failure this deployment actually invites.

The variable names and a first pair of values were written down by the deployment runbook before the code existed: `RATE_LIMIT_REQUESTS_PER_MINUTE=120`, `RATE_LIMIT_BURST=30`. This ADR keeps the names and **replaces the values**, because the first pair was arithmetic done against the wrong unit. It read the fourth fact above as "the effective limit is `limit × workers`, so pick a per-worker number and multiply". The rehearsal showed that a single client does not get the multiplied number: HTTP keep-alive pins a connection to one worker, so one caller draws on one bucket while the others sit idle. Measured on 2026-08-27 against the production-mode stack — the `prod-canary` k6 profile, one subject, 5 arrivals/second for 60 seconds, 4 API workers at 120/minute — **37.9% of 301 requests were refused** with `429`, against a nominal aggregate ceiling of 480/minute for an offered 300/minute. The right way to read the numbers is therefore "what one worker will admit from one client", and the defaults are set accordingly: **600 requests/minute with a burst of 120**.

## Decision

**An in-process token bucket keyed on `(tenant_id, subject)` from the verified token, applied to every authenticated route, returning `429` with `Retry-After` when the bucket is empty.** `src/serving/ratelimit.py` holds it; `src/serving/app.py` installs it between the auth middleware and the audit writer.

- **The key is `(tenant_id, sub)`** taken from `request.state.principal`, which the auth middleware has already resolved from a signature-verified token. `RequestPrincipal.user_id` *is* the `sub` claim — `src/auth/middleware.py` assigns `user_id = str(payload.get("sub"))` and names the field for what handlers use it for — so the bucket follows the account, not the session, the token or the connection. Never a client address, and never a claim the client can set. Buckets are isolated per tenant as well as per subject, so one tenant's traffic cannot throttle another's — the rate-limiting shape of non-negotiable #9.
- **A token bucket, not a fixed window.** A fixed window lets a caller spend a whole minute's allowance in the last second of one window and again in the first second of the next, which is a 2× burst arriving as one spike — exactly the shape the ranking path cannot absorb. Capacity is `RATE_LIMIT_BURST` (120), refill is `RATE_LIMIT_REQUESTS_PER_MINUTE / 60` (10 tokens per second).
- **Headers on every authenticated response.** `X-RateLimit-Limit` is the bucket's **capacity**, not a per-minute quota, because it is the number `X-RateLimit-Remaining` counts down from and a `Limit` that `Remaining` never approaches is worse than no header. `X-RateLimit-Reset` is whole seconds until the bucket is full again — a token bucket has no window to reset. `Remaining` is floored rather than rounded, because a partial token cannot serve a request and advertising it would promise an allowance that does not exist. The sustained rate is not a header; it is in the `429` body, in the OpenAPI description and here.
- **`429` carries `Retry-After`, the three bucket headers, and an `ErrorResponse` body** naming the policy (`"600 requests/minute with a burst of 120"`) so an operator reading a client's log knows which knob produced the refusal. `Retry-After` is whole seconds and never `0`: a client that reads it as "sleep this long" must not spin.
- **`/healthz` and `/readyz` are exempt**, via the same `UNAUTHENTICATED_PATHS` frozenset the auth middleware enforces and the OpenAPI generator reads. They carry no identity to key a bucket on, and a throttled liveness probe takes a healthy service out of rotation.
- **A request with no resolved principal is not charged.** In practice unreachable, since `AuthMiddleware` answers `401` before the limiter runs; the branch exists because the alternative — inventing one shared bucket for every anonymous caller — is a denial-of-service amplifier wearing a limiter's clothes. A limiter fails open on a missing identity or it is not a limiter.
- **Limits come from `Settings`**: `rate_limit_requests_per_minute` (600), `rate_limit_burst` (120), and a tri-state `rate_limit_enabled`. `src/config.py` is the only place they are declared — no Compose file and no env example sets `RATE_LIMIT_*`, because an explicit value in an env example is one copy-paste away from disabling the limiter on a public service. Unset means *on everywhere except a dev box*; setting `RATE_LIMIT_ENABLED` explicitly wins in both directions. A zero or negative limit is refused at construction rather than read as "unlimited" or as "refuse everything" — both `Field(gt=0)` in `src/config.py` and the limiter's own constructor reject it, because `RATE_LIMIT_REQUESTS_PER_MINUTE=0` is a typo and the two readings of it are a silent outage and a silent no-op respectively.
- **The per-tenant quota column on `public.tenants` is the eventual source and is deferred.** It lands with the Phase 6 tenant-config work that also adds the champion-model-version and A/B-seed columns, because that is the work which makes a per-request tenant-config read cached and cheap.

The header names are the `X-` forms rather than the IETF draft's unprefixed `RateLimit-Limit` / `-Remaining` / `-Reset`, on the plain grounds that the `X-` spellings are what clients, proxies and log tooling recognise today while the draft is still a draft. The migration is anticipated rather than assumed: `reliability.py` collects any header whose name starts with `x-ratelimit`, `ratelimit` or `retry-after`, so switching spellings later is a server-side change the required check will not fight.

Three implementation choices are part of the decision rather than details of it, because each one is a question a reviewer asks:

- **It is a raw ASGI middleware, not a `BaseHTTPMiddleware`** — the same choice `RequestIdMiddleware` made, for the same reason. Wrapping `send` in a closure to stamp the three headers costs one closure per request; `BaseHTTPMiddleware` costs an extra task and an anyio memory stream on a path with a p99 SLO. The headers are set on `http.response.start` through a `MutableHeaders` view of the message, so no response body is buffered.
- **The bucket map is guarded by a `threading.Lock` that is uncontended in the deployed shape.** Every route handler in `src/serving/app.py` is `async def` and the middleware is awaited on the worker's own event loop, so a bucket is only ever charged from one thread. The lock exists so that `bucket_count`, or the first synchronous handler someone adds (which Starlette runs in a threadpool), cannot observe or write a half-updated map. `tests/unit/test_ratelimit.py` also asserts that the module imports nothing that could perform I/O, which is the property that keeps `acquire` a dict lookup and some arithmetic.
- **One policy string, three consumers.** `TokenBucketLimiter.describe()` renders "600 requests/minute with a burst of 120"; it appears in the `429` body and in the boot log line that reports `environment`, `dev_auth_bypass` and either the policy or `disabled`. An operator reading a startup log and a client reading a refusal are quoting the same source, so the two can never disagree about what is configured.

### The arithmetic behind the dev exemption

The default is off in `dev` because a per-subject limiter and this project's own load harnesses cannot both be right in the same process, and the harnesses are the ones with a non-negotiable behind them:

| Traffic | Offered, per subject | What it meets at 600/min per worker | Verdict |
|---|---|---|---|
| k6 `smoke` (the CI p99 gate) | 55/s = 3 300/min over many connections | 2 400/min across four workers | 1.4× over on aggregate, and worse on any worker the arrivals favour — the gate would measure the limiter |
| k6 `nightly` | 600/s = 36 000/min | 2 400/min across four | 15× over |
| k6 `prod-canary` (every 30 min, manual) | 5/s = 300/min from one keep-alive client, after a ≤48-request `setup()` burst | 600/min on the one worker it pins, burst 120 | fits with 2× headroom — which the previous numbers did not, see below |
| A browser viewer on `/discover` | a handful per interaction | 600/min | nowhere near |
| `reliability.py`'s probe | 720 rapid requests | 120 on the pinned worker | reaches the floor by design |

The deployed images bake `ENVIRONMENT=production`, so no deployment depends on anyone remembering the variable, and `staging` gets the limiter too. The dev stack — the one place where a single Keycloak identity is asked to impersonate a crowd — is the only place it is off, and ADR 0010's principle is the reason: the gate must measure the service, not the rig. The CI gate is structurally safe either way, because `api-load` runs with `ENVIRONMENT: dev` and `DEV_AUTH_BYPASS: "false"`: real Keycloak tokens, no limiter, which is the combination the pinned p99 threshold was baselined against.

The `prod-canary` row is the one that was wrong, and it is worth stating precisely because it is the whole reason the numbers moved. `canary_thresholds.js` fails on a single non-`200`. `recommendations.js`'s `setup()` warms every worker × persona first — `WARMUP_PER_PERSONA = max(2 × API_WORKERS, 2)` slots across four personas, up to `WARMUP_MAX_ROUNDS = 3` rounds — which at four workers is 64 requests through parallel connections immediately before the measured window. The first pair of numbers made that fit *on aggregate arithmetic and on an even spread across workers*, and the run recorded here is what happens when neither holds: the warm-up spread across all four workers while the measured window rode one keep-alive connection into one of them, and 37.9% of the window came back `429` with 89 warm responses recorded as degraded because a throttled response carries no `serving_policy`. At 600/minute the same client offers 5/s against a 10/s refill on the worker it pins, and the warm-up's 48 requests (at the deployed two workers) sit inside a 120-token burst. If the canary reports throttling again, the fix is still to raise `RATE_LIMIT_REQUESTS_PER_MINUTE` — a variable, not a code change — and never to weaken the canary or exempt its client.

The last row is the one the decision most wants to be true, so its window is sized rather than guessed. `RATE_LIMIT_PROBE_REQUESTS = 720` is `burst + requests_per_minute`, deliberately not `burst + 1`: the probe client's keep-alive connection usually pins one worker and therefore one bucket, where 120 back-to-back requests outrun a 10-per-second refill within a couple of seconds — but a reconnect or an edge proxy can spread it, and then the first bucket to drain needs roughly `workers × burst` plus whatever refilled while those requests were in flight. 720 covers the two workers the deployed API runs with room to spare and the four a Compose stack runs in the pinned case. A deployment with a wider fan-out fails the check with a message saying so and is fixed by `--rate-limit-probe-requests`, not by a code change — a loud, parameterised failure instead of a probe that silently stops proving anything.

### Why not exempt the harnesses by client id

The obvious alternative to the dev exemption is exempting the confidential service client — `movielens-api` is already documented as "trusted for synthetic load and isolation harnesses". It is rejected because it makes the feature unobservable: every harness this project owns authenticates as either `movielens-api` (dev) or `movielens-verify` (production), so an exemption keyed on them means no harness can ever prove the limiter works, and `reliability.py`'s check would have to go back to being advisory. A limiter nothing exercises is a limiter that has already broken.

The narrower version — exempt the service client only where `environment == "dev"` — is what the tri-state setting already achieves, without a code path whose correctness depends on an environment check buried inside a hot function. An exemption list is a thing that grows; a boolean that defaults from the environment is a thing that gets read.

## Consequences

- **The effective limit is *not* `limit × workers` for one client, and that is the correction this ADR carries.** Each uvicorn worker is a separate process with its own bucket map, so the *service* admits `limit × workers` for a subject in aggregate — but a single client with keep-alive holds one connection, lands on one worker, and meets one bucket. The measurement above is what that looks like: 37.9% refused at an offered rate that was 5/8ths of the aggregate ceiling. The numbers are therefore chosen and read per worker. The same fact makes `X-RateLimit-Remaining` **non-monotonic** across a sequence of requests from a client whose connections do spread: consecutive requests read different workers' buckets. The headers are a per-worker view of one caller's allowance, and nothing more; the OpenAPI description says so too.
- **A throttled request still pays for the auth transaction.** The limiter needs the resolved principal, so it runs inside `AuthMiddleware`, which has already opened the RLS-bound transaction and run the tenant-registry `SELECT`. What a `429` sheds is everything expensive — retrieval, the online feature read, ranking, metadata hydration and the audit `INSERT` — but not the pooled connection. Moving it in front of the transaction means moving the check into the auth middleware and coupling rate limiting to token verification; that is a worse boundary for a ~1 ms saving on a rejection path.
- **A `429` writes no `recommendation_audits` row.** The limiter sits outside `RecommendationAuditMiddleware` deliberately: a throttled request produced no prediction to record, and a limiter that turns every rejected request into a durable write amplifies the burst it exists to shed. The cost is that throttling is invisible to the audit SLI the verify job prints — and the second-order version of that cost is worse than it sounds: the SLI under-reports exactly when the service is busiest, so a period of heavy throttling reads as a *quiet* period in the nightly rollup.
- **A `429` leaves no server-side trace at all.** The deployed API runs uvicorn with `--no-access-log` and there is no request-logging middleware, so a refusal is visible to the client in its headers and body, to `reliability.py` as its own evidence, and to nobody else. That is acceptable while the limiter's only observed callers are harnesses; it stops being acceptable the first time someone asks "was a real client throttled last night?", and the answer is a counter in the Phase 5 `/metrics` work rather than turning access logs back on for every request in order to see a few. The 2026-08-27 canary is the worked example: the run's own summary reported 89 "silent learned fallbacks" because a `429` carries no `serving_policy`, which is a refusal wearing a model problem's clothes.
- **The limiter bounds the growth rate of the audit table, not just CPU.** Every admitted recommendation writes a durable row to `recommendation_audits` on a 40 GB disk that also holds both databases, the images and the logs, and `feature_store.*` already grows one generation per release with nothing pruning it (ADR 0013). Capping one subject at 600 admitted requests/minute per worker is therefore also a disk-growth control, which is the part of the case that survives even if the service turns out to have latency headroom to spare.
- **`429` is now in the contract for every authenticated operation.** `docs/api/openapi.json` documents it against `ErrorResponse`, with the four headers defined once under `components/headers` and referenced, and `web/lib/api.generated.ts` is regenerated from it. Documented on the `429` rather than on every response of every operation: the headers are on every authenticated response and the API description says so, and repeating the block roughly 150 times would bloat the committed contract and the generated types without telling a client anything new.
- **The browser reports a `429` as a generic upstream failure.** `web/lib/resources/mapping.ts` maps `429` to the `upstream-error` state with the reason `rate-limited`, and `web/lib/resources/bff.ts` turns that reason back into a `429` at the BFF edge — so the status survives the hop, but the *state* does not, and the region renders "The recommendation API could not answer this request." with a retry affordance. Offering retry is precisely the wrong advice for a refusal that carries `Retry-After`. The reason string already exists, so the fix is a distinct state and a copy string rather than new plumbing; it is not done here because a signed-in viewer would have to be several hundred requests per minute into a session to see one, and because the dev exemption means no browser journey can currently exercise the path end to end.
- **`reliability.py`'s rate-limit check is now required.** It asserts the client-facing contract: the three headers on an admitted response, a `429` with a usable `Retry-After` and a non-empty detail within the probe window, `X-RateLimit-Remaining: 0` on the refusal, and no third status code. It also runs **last**, because it drains the identity's bucket on purpose and every earlier check authenticates as the same subject. What it still cannot assert is that a limiter is *configured*: against a target with no limiter it records that plainly rather than inferring over it, which is the honest shape given the dev exemption above.
- **The verification identity is one subject, and the jobs that share it now share an allowance.** `verify`, `loadcheck` and the reliability harness all authenticate as the `verify` account in the `demo` realm, so they draw on the same bucket per worker. `make prod-verify` runs the matrix and then the reliability harness — which *ends* by draining that subject — and `make prod-load` is the next target an operator reaches for. That chaining is why the Makefile pauses between the two stages, and why the scheduled canary runs the matrix only and leaves the k6 profile to a manual dispatch. A 120-token burst refills in twelve seconds, so the sequence holds comfortably at these numbers; it is written down because "the jobs that check production share one bucket" is not something to rediscover from a red canary.
- **A credential rotation does not reset an allowance, but re-provisioning does.** The key is the `sub` claim, which is a Keycloak user UUID: rotating the `verify` account's password or a confidential client's secret leaves it unchanged, so the bucket follows the account across the rotation — correct, since a rotation should not be a way to buy a fresh quota. Deleting and re-creating an account mints a new UUID and therefore an empty bucket, which is worth knowing before someone treats re-provisioning as a no-op and reads the resulting behaviour change as a limiter bug.
- **The bucket map is bounded at 4 096 live buckets and evicts fullest-first.** A bucket refilled to capacity is indistinguishable from one that was never created, so dropping it changes no future decision; when everything is mid-recovery the caller with the most headroom goes next. Least-recently-used would be wrong here — the least recently *seen* bucket is usually the caller who was just refused and backed off, so LRU would reach the throttled caller first and hand them a fresh allowance, turning the memory ceiling into a way around the limit.
- **The browser is one subject per viewer.** Under ADR 0012 the BFF holds a per-viewer session and calls the API with that viewer's token, so a browser viewer gets their own bucket rather than sharing one with everyone behind the BFF. Demo-persona impersonation does not change this: the bucket follows the *actor*, which is the right unit — the persona is what is being looked at, not who is asking.
- **A deploy empties every bucket.** There is no rolling overlap on a single host — `docker compose up -d` replaces the API container, and the new process starts with an empty bucket map, so a deploy hands every caller a fresh burst. Bounded and harmless for a limiter whose job is to bound sustained cost rather than to enforce a billing quota, and one more reason a durable quota belongs on `public.tenants`. The moment the API runs more than one replica, the effective limit becomes `workers × replicas` and stops being a number anyone can hold in their head — that is the trigger for the shared bucket, not a gradual drift.

## Alternatives considered

**An edge limiter in Caddy.** Attractive because it sheds load before it reaches a Python process at all, which is the one thing the in-process limiter cannot do, and the edge is ours to configure on this deployment. Rejected on what it can key on: the edge sees a TLS connection and an HTTP request, not a verified token. It would have to limit by IP — which collapses every viewer behind one NAT into a single bucket and gives every viewer behind a mobile carrier a shared one — or parse the JWT itself, which duplicates ADR 0007's verification in a component with no access to the JWKS cache and no way to reject a token the API would reject.

The second cost is where the rule would live. Caddy's rate limiting is a third-party module, so an edge limiter means building a custom Caddy image and carrying a module's release cadence for a rule that still cannot see identity. The right place for an edge limiter is in front of a *volumetric* attack, which is a different problem from a single authenticated client overrunning a shared ranker, and it remains available as a second layer if that problem ever arrives — most cheaply as a CDN in front of the two hostnames rather than as a module on the box.

**A Redis-backed shared bucket.** The correct answer and, after the measurement above, the **named follow-up rather than a someday**: one bucket per `(tenant, subject)` in a Lua-scripted atomic token bucket keyed on the tenant-scoped prefix the tenant router already produces, shared across every worker and every replica, exact rather than approximate — and the Redis instance already exists for the online feature store. It is not in this release for two reasons. It puts a network round trip in front of every request on the path the project has a p99 SLO on — sub-millisecond on the host's own Docker network, but paid by every request to save work on the small fraction that get refused.

More decisive is the mode it introduces that the in-process bucket does not have: what the API does when Redis is unreachable. Fail open and the limiter evaporates in exactly the incident where it matters; fail closed and a Redis blip becomes a total outage for a service that can otherwise still serve popularity fallbacks — and note that this API already treats a dependency failure as degradation rather than as an error, so fail-closed would be the only place in the service where an infrastructure blip is fatal. It becomes the right trade the moment the API runs more than one replica, because then the approximation is `workers × replicas` rather than `workers` and stops being explainable. What the rehearsal changed is the honesty of the sequencing: raising the defaults 5× to fit a per-worker reality is a workaround with a limit that no longer means what it says at the service level, and the shared bucket is what lets the numbers come back down to describing one client. It is the next piece of work this ADR names, not a hypothetical upgrade path.

**A per-tenant quota column on `public.tenants`, read per request.** This is where the limits eventually belong — CLAUDE.md's Phase 3 tenant-config bullet already names quotas alongside the champion-model versions and the A/B seed, and a multi-tenant service whose tenants all get the same limit is not really multi-tenant. Rejected as the *first* implementation for sequencing reasons: `src/serving/tenancy/router.py` today resolves only id, display name and Redis prefix, so a quota read would be a new per-request query with no cache in front of it, on the p99 path, to serve a column that currently holds one value for every row.

The cost that decides it is not the query but the cache. Doing this now means designing tenant-config invalidation — how long a stale quota may be served, what invalidates it, whether a quota change needs a restart — before the Phase 6 work that gives that cache three other consumers and therefore the right shape. Building it twice is the expensive outcome, and the shape when it lands is unchanged from this ADR: same key, same bucket, same headers, with the capacity and refill resolved per tenant instead of from `Settings`.

**Deliberate omission — write the ADR that records the gap.** A defensible option and the one the project explicitly left open. The argument for it: the audience is a portfolio reviewer, the traffic is a handful of demo personas, and an unlimited API that says so is more honest than a limiter nobody has load-tested. Rejected because the omission stops being defensible the moment a public hostname exists.

The failure it prevents is not hypothetical for this system — the ranking path writes a durable audit row per request, so an unlimited caller grows a table on a 40 GB disk as fast as it consumes CPU — and "there is no rate limiting" is a much weaker sentence in a design review than "there is a per-subject token bucket, here is why it is per-worker, and here is the Redis upgrade path". The measurement in `reliability.py` was always framed as a gap to close, not a decision; recording it as a decision would have been reading a to-do as a design.

**A concurrency cap on the ranking path instead of an arrival-rate cap.** Worth taking seriously, because what is actually scarce here is not requests per minute but simultaneous work: a bounded semaphore around retrieval-plus-ranking would defend the p99 SLO more directly than a token bucket does, and it would need no per-caller key at all.

Rejected because it protects the wrong thing in the wrong way. A semaphore queues rather than refuses, so the caller that would have been throttled instead makes everyone else's latency worse while it waits — the p99 degrades quietly rather than one client being told plainly to slow down, and there is no `Retry-After` to give a well-behaved client. It is also blind to identity, so it cannot express non-negotiable #9's rate-limiting shape: one tenant saturating the semaphore is indistinguishable from healthy load, which is exactly the cross-tenant blast radius this project treats as its highest-severity class. And it does nothing about the durable cost — a queued request still writes its audit row. The two are complementary rather than alternative; a concurrency cap belongs with the Phase 5 monitoring work that would give it a signal to be tuned against.

**An off-the-shelf middleware (`slowapi`, `fastapi-limiter`).** `slowapi` is IP-keyed by default with a custom key function as an escape hatch; `fastapi-limiter` requires Redis. Both would be a new dependency in the API image — which is deliberately kept slim enough that it imports neither Feast nor LightGBM — in exchange for roughly ninety lines of arithmetic that this project needs to understand in detail anyway, since the per-worker semantics and the eviction policy are the parts a reviewer will ask about.

The subtler cost is defaults. `slowapi` builds on `limits`, whose storage abstraction is the Redis decision above wearing a different hat, and whose in-memory backend has its own eviction behaviour we would inherit rather than choose — including the LRU shape this ADR specifically rejects. A limiter's interesting behaviour lives entirely in the parts a library makes invisible, so writing it is cheaper here than owning someone else's defaults.

## Risks

- **The production canary is the closest thing to a false alarm this decision creates.** Its warm-up spends most of a four-worker burst allowance in one batch and its threshold contract fails on a single non-`200` (see the arithmetic above). Mitigation is that the failure would be loud, immediate and self-describing — a `429` body naming the policy, in a job that runs every thirty minutes and does not gate a deploy — and the response is one variable. This is the first thing to watch on the first canary run after the deployment rehearsal.
- **The dev exemption means the demo stack never exercises the limiter.** Mitigation: `tests/unit/test_ratelimit.py` covers the bucket against a controlled clock and the middleware through a real ASGI app including the header contract, the `429` body and the exemptions; the production-mode rehearsal stack (`make up-prod` → `make prod-verify`) runs `reliability.py` against an `ENVIRONMENT=production` API where the limiter is on, which is the first end-to-end exercise and is part of the deployment rehearsal.
- **The browser's `429` path is unexercised for the same reason.** No Playwright journey can provoke a refusal against a dev stack, so the BFF's `rate-limited` reason and the generic message it renders are covered by unit-level reasoning rather than by a journey. Mitigation: the mapping is a pure function with its own tests, and the rehearsal stack is where a deliberate provocation would go if the state is ever given its own copy.
- **A worker-count assumption is baked into the probe window.** `reliability.py` sends up to 720 requests looking for a `429`, which covers a pinned worker's 120-token burst many times over and a spread across the deployed two workers with margin. A service running many more workers, or one whose client fans out across all of them, might not be throttled inside that window; the check then fails with a message saying so and `--rate-limit-probe-requests` is the fix. This is a deliberate loud failure rather than a silent pass — and it costs 720 requests on a target that is being deliberately drained, which is why the check runs last. The sharper edge is that a probe must **outrun** the refill to drain anything: at ten tokens a second, a client managing fewer than ten requests a second never reaches the floor however many it sends, so a slow link makes this check unprovable rather than failing. It says so in words instead of inferring a verdict.
- **One variable turns the feature off on a public service, and nothing refuses it.** `dev_auth_bypass` is asserted off outside development by `Settings.__init__`; `rate_limit_enabled` deliberately is not, because it has to be settable in both directions for the load rig and the tests, and a guard that refuses `false` in production would also refuse the environment that most needs the escape hatch during an incident. Mitigation is visibility rather than enforcement: the boot log prints `rate_limit=disabled` in the same line as the environment and the bypass state, `reliability.py` reports the no-limiter branch in words that name which stacks are allowed to look like that, and the runbook's symptom table says never to reach for it on a public service. If that turns out to be too soft, the strict form is a preflight assertion in the `release` job, not a constructor refusal.
- **A legitimate client can be refused.** 600/minute per worker is far more than a browser needs and still tight for anything scripted, which is the point: the shape being defended against is a loop, not a person. The `429` body names the policy, which is what makes a refusal diagnosable from a client's log alone, and the response is a config change rather than a code change.
- **Fail-open on a missing principal is a correct rule with a sharp edge.** If a future route is ever mounted outside `AuthMiddleware` but inside the limiter, it is unlimited and nothing says so. Mitigation is structural rather than defensive: `UNAUTHENTICATED_PATHS` is one frozenset read by the middleware, the limiter and the OpenAPI generator, so an unauthenticated route that is not in it fails the contract check before it can quietly become an unlimited one.
- **On the public deployment, most visitors are one subject.** ADR 0013 provisions exactly three accounts and the published one — `walkthrough` — is what a portfolio visitor signs in as, so simultaneous visitors share a single `(demo, sub)` bucket rather than getting one each. The per-viewer bucket described above is a property of the identity model, not of the deployment as provisioned. Mitigation is that the offered rate is tiny (a handful of requests per interaction against 600/minute per worker) and that the real fix is the one ADR 0013 names for the same account: `/me` subject-to-profile ownership, after which a visitor is their own subject and the limiter's unit becomes the one it was designed for.
- **The bucket is memory the process did not have before.** Bounded at 4 096 entries of two floats and a key, so tens of kilobytes; the ceiling exists so that a deployment facing many subjects cannot turn it into an unbounded map. The eviction sweep is O(n log n) but runs only when the ceiling is crossed.
- **Restarts forgive.** A worker restart empties the map, so a rolling deploy hands every caller a fresh burst — twice over during `overlapSeconds`. Acceptable for a limiter whose job is to bound sustained cost rather than to enforce a billing quota — and one more reason the durable quota belongs on `public.tenants` rather than in process memory.

## How we'd know we're wrong

- The `prod-canary` loadcheck starts reporting `429`s in `checks{endpoint:recommendations}`. That means the 1.6× headroom in the table above was not real, and the answer is a higher `RATE_LIMIT_REQUESTS_PER_MINUTE` on `api` — recorded here so nobody reaches for an exemption instead.
- The `verify` matrix or the browser journeys start failing intermittently with `429`. That would mean a single authenticated flow legitimately exceeds 120 requests in a burst against one worker, which is a signal the burst is too small for the product's own interaction patterns rather than that the caller is misbehaving.
- `reliability.py` starts reporting its "advertises a bucket but admitted all N requests" branch. That sentence means the headers describe a limiter that never engages — a bigger problem than a limiter that is too strict, because every client's backoff code is then dead code written against a promise the service does not keep.
- The API ever runs more than one replica. At that point the effective limit becomes `workers × replicas` and stops being a number anyone can reason about; that is the trigger for the Redis-backed bucket, not a gradual drift into a larger multiplier.
- A tenant asks for — or needs — a different limit. The first time the answer to "what is this tenant's quota?" is not "the same as everyone's", the `Settings`-sourced limits are wrong and the `public.tenants` column is due.
- `X-RateLimit-Remaining`'s non-monotonicity turns up as a client bug. If a real client (starting with the BFF) writes backoff logic against these headers and gets it wrong because of the per-worker semantics, the headers are lying by omission and the shared bucket is the fix.
- Anyone asks "was a real client throttled last night?" and the honest answer is that nothing recorded it. With `--no-access-log` and no audit row for a refusal, throttling is currently observable only to the client and to the harness that provoked it; the first time that question is asked in earnest, a counter belongs in Phase 5's `/metrics` work.
- Two portfolio visitors on the shared `walkthrough` account throttle each other. At today's traffic the arithmetic says that cannot happen; if it does, the number of people using one subject has outgrown the account model rather than the limits, and `/me` ownership moves from a product-track item to a prerequisite.
- `bucket_count` sits at the 4 096 ceiling on a service with four personas and a handful of accounts. That would mean the key is wider than the identity — a `sub` that changes per session, say — and the bucket is no longer measuring a caller.

## Note — 2026-08-29: the per-tenant quota column exists, and NULL is how it reads

The alternative above — "a per-tenant quota column on `public.tenants`, read per
request" — was rejected for sequencing, not for design: "`src/serving/tenancy/router.py`
today resolves only id, display name and Redis prefix, so a quota read would be
a new per-request query with no cache in front of it", and the expensive outcome
would have been designing tenant-config invalidation twice.

Migration `0016_tenant_champion_columns` is the work that removes that argument.
It adds the champion-model coordinates, the A/B bucketing seed *and*
`rate_limit_requests_per_minute` / `rate_limit_burst` in one row, and
`TenantRouter` grew the 30-second TTL cache all three consumers share — so the
quota read is a dict lookup on the hot path and one small query per tenant per
window, and the invalidation question was answered once with three consumers in
view rather than once for a limiter.

What the limiter does with the columns, exactly:

- **A tenant with both columns NULL charges the global limiter**, unchanged and
  unallocated. A deployment that sets no quota behaves precisely as it did
  before this migration, which is the state every tenant is in today.
- **A tenant with either column set is charged at
  `COALESCE(column, global setting)`** — each column falls back on its own, so
  lowering one tenant's sustained rate does not require restating a burst that
  was already right. `ck_tenants_rate_limit_positive` refuses a zero or negative
  quota in the database, because a bucket that refuses every request is an
  outage written as configuration.
- **A changed quota takes effect without a restart**, within the router's TTL.
- **The `429` body names the tenant's policy**, not the global one, so a
  refusal stays diagnosable from a client's log alone.

**What is not fixed by this note is the part that matters most.** The buckets
are still per worker whoever configured the numbers, so a four-worker service
still admits `workers × limit` for one subject, and the Redis-backed shared
bucket is still the named follow-up rather than a hypothetical upgrade path.
Per-tenant limits make the number *expressible* per tenant; they do not make it
exact. *(That follow-up landed the next day — see the 2026-08-30 note below,
which also changes how a quota change behaves: the numbers are arguments to the
bucket rather than the key of a cached limiter, so a change no longer rebuilds
anything and no longer hands the affected subjects a full bucket.)*

One entry in "How we'd know we're wrong" above can now be read as satisfied
rather than pending — "the first time the answer to 'what is this tenant's
quota?' is not 'the same as everyone's', the `Settings`-sourced limits are wrong
and the `public.tenants` column is due". The column is there; the `Settings`
values are what a row with no override means.

## 2026-08-30 — the shared bucket lands, and the follow-up closes

Everything above is left as it was written. This note records what changed, because the sequencing is the interesting part: the ADR shipped an approximation, named exactly what was wrong with it, and the next unit of work removed it.

### What the per-worker bucket actually cost

The Alternatives section called a Redis-backed shared bucket "the correct answer" and deferred it for one reason — a network round trip on a path with a p99 SLO — and then the rehearsal added a second, sharper one. The measurement is in the Context above: one subject at 5 arrivals/second against four workers at 120/minute had **37.9% of 301 requests refused**, against a nominal aggregate ceiling of 480/minute for an offered 300. The response at the time was to raise the defaults 5×, which made the canary pass and left the limit meaning something no client could reason about: `X-RateLimit-Limit: 120` on a service that would admit anywhere between 120 and 480 depending on how a caller's connections happened to land.

That is the state this follow-up closes. **One bucket per `(tenant, subject)` now lives in Redis and is charged by a single atomic Lua script, so every uvicorn worker — and every replica, if there is ever more than one — meets the same bucket.** `src/serving/ratelimit.py` holds both implementations; `RATE_LIMIT_BACKEND` selects between them and defaults to `redis`.

### The script, and why each line of it is where it is

```
KEYS[1]  tenant:<tenant_id>:ratelimit:<sub>
ARGV     capacity, refill_per_second, cost, ttl_seconds
returns  {allowed, tokens_left}
```

- **One round trip, one decision.** The read, the refill, the charge and the write happen with nothing interleaved. Two workers charging the same subject in the same instant spend two tokens, not the same one twice — which a read-modify-write from Python could only promise with a second round trip and a lock.
- **The clock is Redis's own `TIME`, never the caller's.** Four workers on one box agree closely enough that it would usually not matter; a caller on another host with a drifting clock could otherwise refill its own bucket by claiming time had passed, which is a limiter that can be argued out of its limit. `TIME` is non-deterministic and was therefore forbidden inside a verbatim-replicated script — Redis has replicated scripts by their effects since 5.0, so this is allowed on every version this deployment can run on. A negative elapsed (a failover onto a replica whose clock is behind) is treated as no time at all rather than as a debt the caller has to pay off.
- **The key sits under the tenant prefix the tenant router already produces.** `tenant:<id>:ratelimit:<sub>`, so a tenant's rate-limit state lives in the same namespace as the rest of its Redis state and a `KEYS tenant:demo:*` sweep finds all of it. `ratelimit.py` deliberately imports no database driver, so it cannot import the router that spells that prefix; a unit test asserts the two spellings agree instead.
- **The TTL is one full refill plus a minute.** A key idle for longer than `capacity / refill` has refilled to capacity, at which point it is indistinguishable from a key that never existed, so expiring it changes no future decision. That replaces the in-process map's 4 096-bucket ceiling and its fullest-first eviction sweep entirely: Redis expires idle keys, and there is nothing left for an eviction policy to get wrong. The sweep survives only in the fallback.
- **Tokens are written back as a string.** A bucket holding 119.4 tokens must not round to 119 on every write, or a caller loses a fraction of a token per request and the configured rate is quietly not the served rate.
- **`EVALSHA` with a `SCRIPT LOAD` fallback**, through redis-py's `register_script`. A Redis restart, a failover onto a replica with a cold script cache, or an operator's `SCRIPT FLUSH` must not turn every request into a 500; the script is idempotent to re-load, and a unit test flushes the cache mid-run to prove the fallback fires.

The header arithmetic — `Remaining` floored, `Reset` as whole seconds to a full bucket, `Retry-After` never `0` — is computed once in Python from the token count either backend returns, rather than twice. That is deliberate: the shared bucket falls back to the in-process one *mid-request*, so a sequence of responses can be served by both, and a client must not be able to tell which answered from the numbers alone.

### Fail open, and why that is the right trade here

**Any Redis error — unreachable, timed out, a script that will not load — charges the in-process bucket for that request instead, and the request carries on.**

The argument for failing closed is real: a limiter that evaporates in an incident is a limiter that is absent in the incident. The argument against it is stronger for this service. A limiter is backpressure, not an auth boundary — nothing about correctness or isolation depends on it, and non-negotiable #9's tenant boundary is RLS, not this. Failing closed would make an unreachable Redis a total outage for a service that can otherwise still serve popularity fallbacks, and it would be the only place in this API where an infrastructure failure is fatal rather than degrading: the sidecars degrade, the feature store degrades, TMDB degrades. A limiter should not be the exception.

What makes it defensible rather than merely convenient is that the fallback is a *real bucket*, carrying the same policy, and not an unconditional yes. The guarantee weakens from "the service admits N" to "each worker admits N" — which is precisely the state this ADR shipped in and survived for a release. That is a bounded, understood degradation rather than an unbounded one.

Three things keep it from being silent:

- **`/readyz` reports it.** The response gained a `rate_limit` field — `shared`, `in-process`, `degraded`, or `disabled` — reported and never gating, on the same terms as the two sidecars. A recent fail-open answers `degraded` without asking Redis anything, because the traffic already answered the question; with no recent failure the probe pings, so a worker that has taken no traffic since boot still reports its dependency rather than its configuration. It does not gate for the same reason the limiter fails open: a deploy that stalls because Redis blinked trades a bounded weakening for an outage.
- **One log line per window, with the count it stands for.** Under a Redis outage at load, a warning per request would bury the incident it is reporting; the line is emitted at most every thirty seconds and carries how many requests it represents plus the running total.
- **`reliability.py` catches it from outside.** Its rate-limit check now fails when the service behaves as though it has more than one bucket, and the failure message names both causes — a `memory` backend, or a shared bucket that is failing open.

The honest limitation: nothing yet counts fail-open events into a metric anyone watches. That is the same gap this ADR already records for `429`s themselves, and it has the same answer — Phase 5's `/metrics` work.

### The one guard `Settings` gained

`RATE_LIMIT_BACKEND=memory` outside `dev` is refused at construction unless `RATE_LIMIT_ALLOW_IN_PROCESS_BUCKET=true` is also set.

The Risks section above explains why `rate_limit_enabled` is deliberately *not* guarded: an operator has to be able to turn the limiter off during an incident, and a guard that refuses `false` in production would refuse the escape hatch at the moment it is needed. The backend is a different question. A limiter that is *on* while admitting `workers × limit` publishes an `X-RateLimit-Limit` no client can plan against — that is not an off switch, it is a wrong answer. Choosing it stays possible, and the flag's name is the acknowledgement; choosing it by omission does not.

### What did not change

- **The limits stay at 600/minute with a burst of 120.** Issue #70 suggested they could now drop "back toward 120/min", and they could — but not to that number: the production canary offers 300/minute sustained from one subject, and against a single shared bucket refilling at 2 tokens a second that would be refused for most of the run. What the shared bucket buys is that 600 now means 600 for the service rather than somewhere between 600 and 2 400; the aggregate ceiling for one subject has in fact *tightened* by the worker count. Lowering the number is a separate decision that wants its own measurement, and the `prod-canary` row of the table above is the measurement it needs.
- **The key, the headers, the 429 body, the exemptions and the middleware position.** Same `(tenant_id, sub)` from the verified token, same three headers, same `Retry-After`, same `UNAUTHENTICATED_PATHS` exemption, same slot between `AuthMiddleware` and the audit writer. A client cannot tell this change happened except that the numbers now add up.
- **The per-tenant quotas the note above added.** They arrived a day earlier against the per-worker bucket and are unchanged in meaning: `COALESCE(column, global)` per column, resolved from the tenant router's cached row through the resolver `src/serving/app.py` injects, with the `429` naming that tenant's policy. What changed is the mechanism underneath them, and for the better. A tenant's numbers are now an argument to the Lua script rather than the cache key of a `TokenBucketLimiter` the middleware kept per tenant, so the per-tenant limiter map and its lock are gone, a tenant with a quota costs no second bucket set, and — the part worth stating — **a quota change no longer hands the affected subjects a full bucket.** The token count lives in Redis and the script clamps it to whatever capacity the request arrives with: lowering a quota discards the surplus at once, and raising one lets the bucket refill *toward* the new capacity instead of filling it. The previous note called the free bucket "the direction to err in"; it is better not to have to err, for the same reason the in-process map evicts fullest-first rather than least-recently-used — whatever a config change does, it must not become a route around the limit for the caller who was just refused.
- **"What limit applies" is still resolved in exactly one place**, now `RateLimitMiddleware._policy_for`. Phase 6's routing work injects a different resolver there and touches neither the bucket arithmetic nor the header rendering.

### Two things measured on the way

- **redis-py's default retry policy is three attempts behind an exponential backoff with a one-second base.** A *refused* connection — which returns instantly — was measured taking **6.7 seconds per call** before the client gave up and the request could fail open. That is sixty-seven times the whole p99 budget, spent inside a middleware whose entire promise is that it costs one round trip. The client is built with `Retry(NoBackoff(), retries=0)` and a 50 ms socket and connect timeout; the same measurement then costs **0.2 ms**. This is the kind of default that is invisible until the day it matters, which is exactly the day it must not cost anything.
- **The script's own cost is about half a millisecond over a bare `PING` on the same connection.** Measured from a laptop through Docker Desktop's port forward — not the deployed path, where it is a hop on the host's private Docker network — the bare `PING` ran p50 0.66 ms / p99 7.24 ms and the full charge p50 1.17 ms / p99 28.66 ms over 300 samples each. The jitter is the transport, not the bucket. The number that matters is the delta, and it is small; the number that would matter more is the one from the deployed host, which the production canary will produce.

### How we'd know this is wrong

- **`/readyz` reports `rate_limit: degraded` for anything but a moment.** The limiter is then per worker with extra steps, and the question is why Redis is unreachable from a container on the same bridge network as the one the online store already serves.
- **`reliability.py`'s new bounds fail on a deployment nobody changed.** Either the arithmetic is too tight — it derives its allowance from the service's own `X-RateLimit-Reset`, so a rounding assumption is the first place to look — or the service really did hand out more than one bucket's worth, which is the finding it exists for.
- **The round trip shows up in the p99.** The CI gate cannot see this — `api-load` runs with the limiter off, deliberately, so the gate measures the service rather than the rig — so the signal is the production canary's recorded p99 moving with no other change. If it does, the answer is not to remove the limiter but to look at what a `SCRIPT` call costs on that box next to the `fdatasync` the audit row already pays.
- **A worker restart stops forgiving.** The old bucket lived in process memory, so a deploy handed every caller a fresh burst; the Consequences above say so twice. It does not any more — a Redis-held bucket survives the deploy. That is the correct behaviour and it is also a behaviour change: if a deploy ever appears to leave a caller throttled, that is why, and the bucket refills at the configured rate exactly as it would have.
