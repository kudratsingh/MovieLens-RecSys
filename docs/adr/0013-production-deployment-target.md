# ADR 0013 — Production Deployment Target: One Hetzner VPS

**Status:** Accepted
**Date:** 2026-08-27

> This ADR replaces an earlier draft on the same branch that chose Railway. That draft was never merged and nothing was ever created on Railway, so it is rewritten here rather than superseded by a new number — the decision line has one entry because only one decision was ever landed. The platform-agnostic work the draft produced (`docker-compose.prod.yml`, generated secrets, the release and verify jobs, the backup and restore drill, the boot guardrails) is unchanged, and is what makes this choice cheap to make.

## Context

Phase 3 is code-complete and has never been deployed. Until the production-mode rehearsal, **no job in this repository had ever started the application with `ENVIRONMENT != dev`** — the `Settings` guardrails that refuse a dev auth bypass and a default sidecar token outside development had never once fired against a real boot, and `environment` was an unvalidated `str`, so `"prod"`, `"prd"` and `"Production"` all silently satisfied every `!= "dev"` check.

That rehearsal now exists. `docker-compose.prod.yml` is the deployment's topology in Compose form — `ENVIRONMENT=production` everywhere, no `DEV_AUTH_BYPASS` variable at all, generated secrets from a gitignored `.env.prod`, `scram-sha-256` through pgBouncer's forced-user aliases, a Caddy edge terminating TLS on real hostnames, and no published port except the edge — and it has been driven from empty volumes through `make prod-reset && make prod-seed && make prod-verify` more than once. So the open question is no longer *what shape does production take*. It is **whose computer runs it**, and that turns out to be a much smaller question than it looked before the shape existed.

Four code facts still do the eliminating, because they are what a platform has to accommodate:

- **Migration `0001` creates `admin_user` and `migrator` with `BYPASSRLS`.** That needs a true Postgres superuser. Any platform whose managed Postgres withholds superuser cannot run this project's first migration without an ADR 0008 amendment.
- **The API refuses to boot without pgBouncer's admin console** and asserts `pool_mode = transaction` there (`src/serving/startup_checks.py`). Session-mode pooling would preserve `SET LOCAL app.tenant_id` across transactions, which *is* the cross-tenant leakage class, so the pooler is our own service or the check is weakened.
- **The serving bundle and the Feast registry are files two sidecars read once, in `lifespan`.** They are baked into the features image (247 KB of deterministic build output), which is what makes rolling back the model the same action as rolling back the image.
- **Keycloak's JVM cold start is 8–15 s and the model-server warms every worker inside `lifespan` before `/healthz` returns 200.** Any platform that suspends idle machines turns both of those from a startup cost into a user-visible defect after every quiet period.

The rehearsal also settled two things that would otherwise have been decided by a platform: pgBouncer runs in `userlist` mode rather than `auth_query`, because both `[databases]` entries pin a forced user and a pooler that opens the server connection under its own identity has no SCRAM exchange to pass through — measured, not preferred; and ADR 0014's rate limiter turned out to be a per-worker number rather than a per-service one, which a single-host deployment has to size deliberately. Neither is a hosting question, and both are the kind of thing that is much cheaper to discover on a laptop than on a first deploy.

The fifth fact is money. Measured idle RSS across the nine long-lived services is ≈2.0 GB, which at Railway's usage pricing is **≈$27/month** all-in — about $324 a year, indefinitely, for a portfolio system with four demo personas and one owner. The criteria, in the order they eliminate options: (a) can it run migration `0001`; (b) does the public/private split survive, given that `feature-server` has no authentication of any kind; (c) does it ever suspend; (d) what are the actual commands for a deploy, a rollback and a restore, and who runs them at 02:00; (e) what does it cost per month *and* in attention.

## Decision

**Production is one Hetzner Cloud CX22 — 2 shared x86-64 vCPU, 4 GB RAM, 40 GB NVMe, Ubuntu 24.04 — running `docker-compose.prod.yml` unchanged behind its own Caddy edge with `EDGE_TLS=acme`.** Deliberately x86-64 and not the cheaper ARM CAX line: every image this project publishes is `linux/amd64`, and an ARM host would mean a second architecture built and proven for the FAISS, LightGBM and Feast wheels in exchange for about a euro a month.

The concrete shape, all of it named so that two workflows, one script and this document agree:

- **Host layout.** The repository is checked out at `/opt/movielens`, owned by an unprivileged `deploy` user; secrets live in `/opt/movielens/.env.prod` at mode 0600 and never in git; the running release is recorded in `/opt/movielens/.release/current` and `.release/previous`, which is what makes a rollback target something that was written down before the incident rather than reconstructed during it.
- **The box never builds.** CI publishes every image to GHCR as `ghcr.io/kudratsingh/movielens-recsys/<name>:<tag>` for `api`, `features`, `web`, `pgbouncer`, `keycloak`, `backup` and `k6`, tagged with both the 40-character commit SHA and a moving `main`. The Compose file resolves `${IMAGE_REPOSITORY}` and `${IMAGE_TAG}` while keeping its `build:` contexts, so `make up-prod` still builds locally for the rehearsal and the host only ever pulls.
- **Host preparation is a script, not a checklist.** `infra/host/bootstrap.sh` is idempotent: the `deploy` user and its SSH key, password authentication off, `ufw` allowing only 22/80/443, unattended security upgrades, Docker CE with the compose plugin from Docker's own apt repository, `/etc/docker/daemon.json` with `json-file` rotation at 20 MB × 5 per container, and three systemd units — `movielens.service` (bring the stack up at boot), `movielens-backup.timer` (nightly 04:00 UTC) and `movielens-prune.timer` (weekly image prune older than 7 days, **never** volumes).
- **Deploys are `infra/deploy/deploy.sh <sha>`**, run over SSH by `.github/workflows/deploy-production.yml` after CI succeeds on `main`: pull at that SHA, run the release job (idempotent Keycloak provisioning, then preflight → schema → seed → materialize through the existing `prod-*` Makefile targets), `up -d`, then `make prod-verify`. **A failed verification rolls back to `.release/previous` automatically and verifies again**, and the script prints `DEPLOY-OK <sha>` or `ROLLBACK-OK <sha>` so the workflow fails loudly when neither appears. `deploy.sh --rollback` is the same path by hand.
- **The public surface is two hostnames and nothing else.** `PUBLIC_APP_HOST` → `web`, `PUBLIC_AUTH_HOST` → `keycloak`, both terminated by the edge with Let's Encrypt certificates. Every other service is reachable only on the host's private Docker network; the only ports bound on the host are 80 and 443 (the edge) and 22 (SSH, key-only).

The release order is part of the decision rather than an implementation detail, because the steps fail closed against each other and a deploy that runs them out of order hangs rather than errors:

1. `docker compose pull` at `IMAGE_TAG=<sha>` — every image for this release lands on disk before anything is stopped, so a registry problem is a no-op rather than a half-deploy.
2. The data stores and the pooler, then `keycloak`, whose healthcheck deliberately probes the `master` realm's discovery document: on a first deploy the `demo` realm does not exist yet, and probing a realm a later step creates would deadlock the deploy forever.
3. Keycloak provisioning — idempotent, and provisioning a tenant means creating a realm **and** a `public.tenants` row; either alone fails closed.
4. The release job: preflight (including issuer equality against the live discovery document), then schema, then seed, then materialize. The order matters because the model sidecar refuses to boot against an unmaterialized Redis rather than serving zeros.
5. `feature-server`, `model-server`, `api`, `web` — the API cannot become ready until the serving realm's JWKS is fetchable and the schema exists, which is why it comes after both.
6. `make prod-verify`, and on failure the automatic rollback to the previous SHA followed by a second verify. The exit code is the deploy's verdict; the sentinel line is how the workflow reads it.

## Rationale

1. **The deployment artifact already exists, and this platform runs it unmodified.** Every hour spent on the rehearsal produced something the host consumes directly rather than a translation of it. That is the difference between a deployment and a port: there is no second description of the topology to keep in step, so the class of bug where the rehearsal and production diverge silently cannot occur — they are the same file, with different values for `IMAGE_TAG` and `EDGE_TLS`.

2. **Owning the machine dissolves three of the four code facts instead of working around them.** Postgres runs in a container we start, so its superuser is ours and migration `0001` runs. The pooler is our own service, so the admin console the boot check needs exists and `pool_mode` is what we set it to. The sidecars share a host filesystem and a Docker network, so nothing about the bundle, the registry or `admin_user`'s direct-to-Postgres reads needs re-engineering. The fourth — never suspend — is free on a VPS that is simply always on.

3. **Cost, which is the deciding factor and is honest about being one.** €4.50/month against a measured $27, for the same ≈2.0 GB footprint. The gap is not buying capacity we use: it is buying a control plane, per-service billing granularity and managed volume snapshots for a system that self-hosts its database, its pooler and its identity provider anyway. Over a portfolio system's realistic lifetime that is roughly $270 a year of difference, and the operational surface it removes is smaller than it appears once you notice how much of the stack we were already running ourselves.

4. **Images come from CI, not from the box.** A CX22 has two shared vCPUs and 4 GB, and the features image installs Feast, LightGBM, FAISS and pandas — building that on the host while it serves would be a self-inflicted outage. Publishing to GHCR also makes the deploy and the rollback the same mechanism (`IMAGE_TAG=<sha>`, `docker compose pull`, `up -d`) rather than two, and makes "what is running?" answerable from a file on disk instead of from a provider's dashboard.

5. **Verification and rollback were already scripted; SSH just invokes them.** `make prod-verify` runs the post-deploy matrix and exits non-zero on any row — issuer equality, cold-start and learned serving, the auth boundary, cross-tenant isolation, a write round trip, realm invariants, the audit SLI, artifact provenance — followed by the non-latency reliability harness. A deploy path that ends in that command, and that rolls back and re-runs it when it fails, is a stronger guarantee than most managed platforms offer, because it is asserting about *this* application.

6. **What this gives up is small *for this system* and would be disqualifying for a different one.** There is no horizontal scaling, no zero-downtime deploy, no failover and no managed snapshot button. Every one of those matters when traffic or an SLA justifies it; none of them is exercised by four demo personas and a portfolio reviewer, and buying them now would mean paying for capability in exchange for the one thing this project cannot get more of, which is the owner's attention. The trigger that flips each of them is written into "How we'd know we're wrong" rather than left as taste.

## Alternatives considered

- **Railway, the previous draft's choice.** It is genuinely well-shaped for this system: a private WireGuard mesh where nothing is published by default, a `postgres` role that really is a superuser, run-to-completion jobs with cron schedules, and pre-deploy commands that abort a deploy on a non-zero exit. The rejection is the measured $27/month against €4.50 for a portfolio system, and two second-order costs the price tag hides. Volumes are per-service and not shareable, so the shared-filesystem shape had to be redesigned into baked artifacts (a good change we kept, but one the platform forced). And rollback is not a command: the pinned CLI cannot reach a specific previous deployment — `railway redeploy` takes no deployment id and `railway down` *deletes* the latest deployment — so both workflows had to drive the GraphQL API and record every service's deployment id before touching anything. On a single host, rollback is a SHA in a file. Railway stays the obvious answer if this ever needs more than one machine's worth of scheduling, and the Compose file remains the input either way.

- **Oracle Cloud Always Free.** The only option with a $0 line, and the one that looks best until you read the terms. The free allowance is ARM (Ampere A1), which means every image needs an `arm64` build and, more to the point, needs *proving* on arm64 for FAISS and LightGBM before anything can be trusted; the allowance has been trimmed for newer accounts, so the headline capacity is not what a new tenant gets; and Oracle reserves the right to reclaim idle Always Free compute. A portfolio demo is idle by definition between visitors — an instance that can be reclaimed for not being busy is precisely the wrong host for a system whose whole value proposition is that it is up when someone opens the link. Free stops being free the first time it disappears and the recovery is a fresh restore drill.

- **A DigitalOcean Droplet with Coolify on top.** The nearest neighbour to the decision: the same Compose file, the same self-hosted everything, plus a web UI for deploys, environment variables and logs. Two things sink it. The price is roughly five times Hetzner's for the same 4 GB / 2 vCPU shape, which is the whole reason this ADR is being rewritten. And Coolify is a control plane — another service on the box holding the deployment's credentials, with its own upgrade cadence, its own failure modes and its own opinions about how a Compose file should be run. It would be earning that keep if it replaced work we do not want to do; what it actually replaces is `docker compose pull && docker compose up -d` and a `make` target, both of which are already written, reviewable and testable in CI. A UI we would open twice is not worth a permanent daemon.

- **Keep it on the laptop behind a tunnel** (Cloudflare Tunnel or similar). $0, no new provider, and the demo stack already runs there. Rejected because it fails the thing the deployment exists to prove. The machine sleeps, so the link is dead exactly when a reviewer clicks it; the "deployment" is a process someone started by hand, so there is no release, no rollback target and no unattended restart; a tunnel puts an authenticated ML API and an IdP admin console on a home network's address; and none of the specific engineering this phase is about — a real issuer over TLS, secrets that are not fixtures, an ordered release with a recorded rollback target, backups off the machine — gets exercised. It is the status quo with a URL bolted on.

- **Managed Kubernetes**, mentioned to be dismissed with a reason rather than by omission. It is the correct answer at the far end of this project's phase plan, and CLAUDE.md already keeps k3s/kind as optional after Phase 4. It is disproportionate now: nine long-lived processes with one owner do not need a control plane, an ingress controller and a secrets operator, and on the major clouds the managed control-plane fee alone exceeds this entire deployment before a node is billed. The decisive argument is not cost, though — it is that the first production deployment of this system would also be the first Kubernetes deployment, two unknowns at once, on the layer where a mistake is a cross-tenant incident.

## Sub-decisions recorded here

- **`/readyz` remains a second unauthenticated path.** Non-negotiable #10 names `/healthz` specifically and forbids "internal" unauthenticated paths, so widening it stays recorded rather than quietly done. On one host the forcing fact is the same in a different costume: the Compose healthcheck and the deploy script's readiness poll carry no `Authorization` header, and an authenticated readiness path means a deploy that can never confirm itself. What the endpoint may tell an anonymous caller is unchanged — can this process reach its own database through the pooler, and can it fetch the serving realm's JWKS, plus a non-gating `ok`/`unavailable` for the two sidecars. No tenant id, no user data, no model version, no counts. It answers on a container port that is not published and that the edge does not route, so the only callers are on the host's private network. The set is one `UNAUTHENTICATED_PATHS` frozenset in `src/auth/middleware.py`, read by the middleware, the rate limiter and the OpenAPI generator, so it cannot grow in one place only. `/metrics` is still deliberately not added: a scrape endpoint carries per-tenant counts and latencies, there is no authentication story for a scraper yet, and Phase 5 owns it.

- **Postgres traffic stays on the host's private Docker network, and TLS to Postgres is still not required in code.** Every DSN in `src/config.py` is built by f-string concatenation with no query-parameter hook and Feast's `feature_store.yaml` hardcodes `sslmode: disable`, so requiring TLS would mean editing the credential path in the same release as the first production boot. On a single host the traffic never leaves the kernel: the databases, the pooler and Redis publish no host ports at all, and pgBouncer's `server_tls_sslmode = prefer` still gives the `app_user` leg opportunistic TLS. This is written down because it stops being true the moment anything moves off this box — a second node, a managed Postgres, an external analytics consumer — and at that point a `sslmode=require` DSN parameter and a Feast config change are prerequisites of the move, not follow-up work.

- **GHCR is the image source of truth, and the SHA tag is the release identity.** Nothing is built on the host and nothing is built during an incident. The consequence is that the weekly prune keeps seven days of images so the previous release is always local, and that a rollback further back than that is a `docker compose pull` away *provided the tag still exists in the registry* — which is why the publish job pushes the immutable SHA tag alongside the moving `main` one, and why no retention policy that expires SHA tags may be enabled on the package.

- **The rehearsal stack and the deployment are one file, and the two differences are named.** `docker-compose.prod.yml` keeps its `build:` contexts so `make up-prod --build` still produces images locally, and the host sets `IMAGE_TAG` to a SHA so `docker compose pull` resolves the same service names to published images instead. The other difference is `EDGE_TLS`: `internal` uses Caddy's own CA against `app.localtest.me` for the rehearsal, `acme` gets Let's Encrypt certificates for the real hostnames. Everything else — service names, healthchecks, dependency order, environment contracts, the release and verify jobs — is shared, which is the property that makes the rehearsal evidence about production rather than about a lookalike.
- **Secrets live on the box in one 0600 file, with the password manager as the authority.** There is no variable panel and no provider-side secret store, so `.env.prod` on the host is the only runtime copy and GitHub holds only what the deploy path needs (`DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`). The generation rule is not cosmetic: every DSN in `src/config.py` is f-string-concatenated with no URL-encoding, so `secrets.token_urlsafe(48)` is the rule and `openssl rand -base64` is not, because a password containing `@` mis-parses the host and one containing `%` is percent-decoded. Rotation is an edit to that file plus a re-run of the idempotent provisioning SQL, not a support ticket.

## Consequences

- **One failure domain, stated plainly.** The host is the database, the identity provider, the ranker, the edge and the web app. A kernel panic, a full disk or a failed reboot is a total outage, and there is no failover to fail over to. What makes that acceptable is the recovery story being real rather than implied: nightly `age`-encrypted `pg_dump`s of both databases pushed to an off-box bucket, a restore drill with an exit code (`infra/backup/restore-drill.sh`), and a host that can be recreated from `infra/host/bootstrap.sh` plus a checkout plus `.env.prod`.
- **A deploy is a brief outage, not a rolling update.** `docker compose up -d` recreates the containers whose image changed; the API and web come back in seconds, Keycloak in 8–15, and the model-server only after every worker has warmed. There is no second replica to shift traffic to and no `overlapSeconds`. At this traffic level that is the right trade, but it means deploys are a thing you do deliberately rather than something a viewer never notices.
- **Patching is the owner's job now.** Unattended upgrades install security updates, but kernel and Docker upgrades that need a reboot are a manual, scheduled act — and a reboot is a full outage (`movielens.service` brings the stack back, which is why it is a unit rather than a habit). The managed-platform version of this line was "the provider patches the host"; that sentence is gone.
- **Per-service resource limits become load-bearing at 4 GB.** Every service carries a memory limit in `docker-compose.prod.yml` and Keycloak's heap is capped explicitly, because the failure mode without them is the kernel's OOM killer choosing a victim by heuristic, in production, at whatever moment memory peaked. The sizing lives in `infra/deploy/production.env.example` and is tuned to what the rehearsal measured rather than to what looks generous.
- **Disk is a budget, not an assumption.** 40 GB holds the images (two releases' worth after the prune), both Postgres volumes, Redis, Caddy's certificate store and the logs. Container logs are rotated at 20 MB × 5 per container by `/etc/docker/daemon.json`, and the weekly prune removes images older than seven days and **never** volumes. `feature_store.*` still grows one generation per release with nothing pruning it, which on a fixed disk is a slow leak rather than a slow bill.
- **The SSH deploy key is a root-equivalent credential.** `deploy` is in the `docker` group, so a compromise of the GitHub `production` environment's `DEPLOY_SSH_KEY` is a compromise of the host. It is scoped to one key, one user and one machine, `known_hosts` is pinned from a secret so the workflow never trusts a new host key, and password authentication is off — but the honest framing is that this trades a provider's API token for an SSH key, not that it removes the credential.
- **Personas still reset to seed state on every release**, because the seeder is idempotent by delete-then-insert over nine known user ids in tenant `demo`. That is what makes the smoke assertions deterministic and it also wipes any movie state a visitor created. User-visible; it belongs on the sign-in door, not only in a runbook.
- **Audit coverage is recommendations-only in production too.** `src/serving/audit.py` matches `^/users/(\d+)/recommendations/?$`, so mutations pass through unaudited. Deploying does not change that, and the runbook says so rather than letting CLAUDE.md's "every authenticated request emits a row" read as a description of what is running.
- **The whole bill is legible.** The server and its IPv4 address are the recurring line; the off-box backup bucket fits inside a free tier at this data size; the domain is already owned. Nothing scales with request count, which means the cost of leaving this up for a year is knowable in advance rather than a graph to watch — the failure mode a usage-priced platform has, where a loop in a client turns into an invoice, does not exist here.
- **DNS is part of the deployment now.** Two A records point at the machine's address, and the issuer in every token is derived from one of them, so moving the box means moving DNS and waiting for it — with an issuer change that must land in Keycloak, the API and the web app in the same window or every request 401s. Keeping the TTL modest is the cheap insurance; the expensive version of learning this is discovering during a migration that the records were cached for a day.
- **Observability is what the box gives us plus what we already built.** There is no provider dashboard: the signals are `docker compose ps`, rotated container logs, `docker stats`, the nightly verify job, the 30-minute canary and the audit SLI that verify prints from `recommendation_audits`. That is thinner than a managed platform's, and it is also the same set the rehearsal debugged against — Prometheus and Grafana arrive with Phase 5, and until then a health question is answered by running the matrix rather than by reading a graph.
- **Realm changes made in the console or by `kcadm` must be exported back into git**, or the templates under `infra/keycloak/realms/` drift from reality permanently. `--import-realm` never overwrites a realm that already exists, so editing the JSON after first boot would have no effect while looking like it did. That was true on any platform; it is worth repeating here because the console is now reachable at `https://<PUBLIC_AUTH_HOST>/admin` and the temptation is one click away.
- **Non-negotiables #2, #4 and #11 keep CI as their only authority.** Feature parity has no remote-executable form; the pinned load gate needs Compose recreation, `docker stats`, cgroup reads and a `/proc/stat` probe. The deployment adds the nightly verify and a 30-minute canary, and says plainly that they are weaker instruments — the canary enforces correctness and the warm-traffic `learned` assertion, and records p99 with no verdict.

- **CI grows a publishing job, and `main` grows a deploy trigger.** `publish-images` runs only on a push to `main` and only after every other job has succeeded, so an image that exists is an image whose commit passed the gates; `.github/workflows/deploy-production.yml` then fires on that workflow run and re-asserts the SHA's CI conclusion before it opens an SSH connection. The second-order effect is that merging to `main` is now a production action. That is the intent — but it means a docs-only merge restarts containers, and the `changed-paths` filters that keep CI cheap do not make a deploy cheap.
- **Two GitHub environments exist for one target.** `production` carries the deploy credentials behind whatever protection the owner wants; `production-canary` carries the same values with **no** protection rules, because a required reviewer on a job that fires every thirty minutes is not a canary. Both share the `production-hetzner` concurrency group with `cancel-in-progress: false`, so a canary can never overlap a deploy on the one host they both drive.
- **The rate limiter's defaults are now a deployment-shaped number.** ADR 0014's bucket is per worker, and the rehearsal measured what that means for a single keep-alive client; the defaults it settled on (600/minute, burst 120) assume the two API workers this machine runs. A different worker count is a different effective limit, which is one more reason `API_WORKERS` belongs in the sizing file next to the memory limits rather than in three places. *(Superseded 2026-08-29: the bucket moved into Redis and is shared by every worker, so the defaults no longer depend on `API_WORKERS` — see ADR 0014's note of that date. The rest of the reasoning for keeping `API_WORKERS` in the sizing file stands on its own.)*

## Risks

- **4 GB is the binding constraint, and the rehearsal measured it on a machine with more.** Idle RSS is ≈2.0 GB, which leaves headroom for exactly one thing to misbehave. Mitigation: explicit memory limits everywhere, a capped Keycloak heap, two API workers rather than four, and the knowledge that the first symptom of getting this wrong is a container disappearing rather than an error — check `docker inspect`'s `OOMKilled` before reading application logs.
- **Shared vCPU with no steal visibility of the kind ADR 0010 requires.** The measurement-validity rule depends on the host's CPU-steal record; on a shared-vCPU VPS that record exists but the neighbours do not. Mitigation is the two-tier framing that already applies: CI keeps the verdict, the production canary records p99 without one, and a persistent gap between them is an investigation trigger rather than a reason to re-baseline.
- **Let's Encrypt rate limits are a real way to lock yourself out of your own edge.** Caddy stores certificates in the `caddy_data` volume; a rebuild loop that deletes that volume can exhaust the duplicate-certificate allowance for the week and leave the site on an untrusted certificate. Mitigation: never `down -v` on the host, and rehearse edge changes locally with `EDGE_TLS=internal`.
- **The first deploy has an ordering trap that only bites once: certificates need DNS.** Caddy cannot complete an HTTP-01 challenge until both A records resolve to the machine and port 80 reaches it, and until it has a certificate the OIDC round trip cannot be tested at all. Mitigation is to create the records before the first `deploy.sh` run and to verify the edge's certificate before reading any auth failure as an auth problem — a `SEC_ERROR`-shaped browser error and a misconfigured issuer look identical from the application's side.
- **Two firewalls that can disagree.** The Hetzner Cloud Firewall filters before the packet reaches the machine and `ufw` filters on it; a rule added to one and not the other presents as "the port is open but nothing answers" or the reverse. Both are documented as 22/80/443 only, and neither is edited during an incident without writing down which one changed.
- **The load generator now shares two vCPUs — and one rate-limit bucket — with the service it measures.** k6 runs on the same host, so a heavier profile would be measuring contention it created; and it authenticates as the same `verify` subject the matrix does, so back-to-back runs draw on one token bucket. Both are why the scheduled canary runs only the verify matrix and the k6 run is manual and advisory, and both are reasons ADR 0010's CI gate keeps the verdict.
- **A GHCR outage or a mistyped tag blocks a deploy.** Mitigation: the previous release's images are on the box until the weekly prune, so `deploy.sh --rollback` does not need the registry; a *forward* deploy does, and that is an acceptable dependency for an action nobody has to take at 02:00.
- **pgBouncer remains a single point of failure the API refuses to boot without.** By construction: the check that proves transaction pooling is also a hard dependency on the pooler being up. Accepted, because the alternative is an API that can boot into a configuration where `SET LOCAL app.tenant_id` leaks across requests.
- **Any signed-in `demo`-realm account can read and mutate all four personas.** There is no `/me` subject-to-profile ownership yet (ADR 0012 names it as future work), so on a public URL the blast radius of one account is the whole demo tenant's product surface. Mitigation: registration disabled, three deliberately-created accounts, the `isolation` account deliberately without the impersonation role so the canary has a subject that must be denied, and a line on the sign-in door.
- **The Keycloak admin console is internet-reachable, and no path-level ACL fronts it.** That is structural rather than an oversight: the edge routes a hostname, not a path policy. Mitigation is a long generated realm-admin password that lives only in the host's `.env.prod`, a separate named human admin as the account anyone actually signs in with, brute-force protection on both realms, and `registrationAllowed: false`. Deleting the admin credential is *not* available: provisioning is idempotent and re-runs on every deploy with it, and the Compose model declares it required, so its removal fails the next release at interpolation. Retiring the console account means moving provisioning onto a service-account client, which is a code change. A Caddy matcher restricting `/admin` to a known address is the stronger form and remains one edge-config change away.
- **Rotating `MODEL_SERVER_AUTH_TOKEN` on one service and not the other degrades every recommendation to popularity at HTTP 200**, not to an error, because the coordinator treats a sidecar rejection as unavailability and falls back. Rotate it in a window and let the verify job's learned-path assertion confirm recovery — this is the failure mode most likely to be mistaken for a model problem.
- **The deploy path runs the release job on every deploy, including a rollback.** Mitigation is unchanged and load-bearing: additive migrations only, a schema step that exits 0 when the database is ahead of the image, and a rehearsed restore as the rollback path for any release that must ship a destructive migration.

- **Port 22 has to be reachable by GitHub's runners, which means reachable.** GitHub does not publish a small, stable egress range worth pinning a firewall to, so the practical configuration is SSH open to the internet with password authentication disabled and only the `deploy` key trusted. The compensating controls are that the key is one credential in one environment, `known_hosts` is pinned from a secret so a substituted host key fails the deploy rather than trusting it, and `ufw` still refuses everything else. A self-hosted runner on the box would remove the exposure and add a permanent process holding a GitHub token; that trade is worth revisiting only if the SSH surface ever produces an incident.
- **One provider, one region, one machine.** A Hetzner outage, an account problem or a hardware failure takes the whole system with it, exactly as the single-failure-domain consequence says. Mitigation is that the recovery path leaves the provider: backups go to a different vendor's bucket, encrypted client-side, and the host is reproducible from a script and a checkout — so the worst case is measured in hours of restore rather than in lost data.

## How we'd know we're wrong

- **The box needs attention more than about once a month.** The entire case for a single VPS is that the operational surface is small enough for one person to carry alongside the ML work. Recurring OOM kills, disk pressure, or a deploy that needs hand-holding would mean the ~$22/month saved is being spent in hours at a much worse exchange rate.
- **Memory pressure shows up in the audit SLI rather than in `docker stats`.** If p99 or the learned-vs-fallback ratio degrades on a schedule that matches the nightly backup or the weekly prune, the machine is too small for its own housekeeping and the answer is a CX32, not a tuning session.
- **The deploy blip becomes something anyone mentions.** Nobody should notice a portfolio system restarting. If someone does, that is the signal that this needs two replicas behind the edge, which is the point at which a single host stops being the right shape rather than a cheap one.
- **A restore is ever needed and the drill has drifted.** The drill has an exit code precisely so this is testable in advance; a real restore that needs improvisation means the drill stopped describing the system, and every manual step taken becomes a ticket.
- **A second serving tenant becomes necessary.** The sidecar is pinned to `manifest.tenant_id` and 403s any other, so a second serving tenant is a second process on a 4 GB machine. That would mean Phase 6's tenant-aware routing has arrived early and the sidecar needs a multi-bundle registry.
- **The verify matrix goes green while the product is visibly broken.** It asserts persona slugs, policies, the learned flag, the auth boundary, isolation denials, a write round trip and the audit rollup. If a real regression walks past all of that, the matrix is under-specified and the fix is a new row — this is the check we would most like to be told is insufficient, and a 30-minute canary that only exercises the recommendations path is a thin backstop for it.
- **Anything is fixed by hand on the box and the fix is not written back into a script.** A single host makes hand-editing possible in a way a PaaS did not, which is a convenience and a trap: the next deploy overwrites the containers and the fix disappears, or worse, it does not and the box stops matching the repository. Any manual step that survives a session belongs in `infra/host/bootstrap.sh` or `infra/deploy/deploy.sh` the same day.
- **The k6 canary's p99 sits persistently above CI's at one-eleventh the arrival rate.** At ~5 arrivals/second against 55 in CI, production should not be the slower of the two. If it is, the suspect is the shared vCPU, and the answer is dedicated capacity — never a threshold change.
