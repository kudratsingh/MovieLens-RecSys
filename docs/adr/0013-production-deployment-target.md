# ADR 0013 — Production Deployment Target: Railway

**Status:** Accepted
**Date:** 2026-08-26

## Context

Phase 3 is code-complete and has never been deployed. Everything this project claims about itself is currently proved on one laptop: the auth boundary, the tenant-isolation canaries, the pinned p99 gate, the browser journeys and the frontend finish gate all run against `docker-compose.yml` + `docker-compose.demo.yml`. `docker-compose.{staging,prod}.yml` have been listed in CLAUDE.md as planned and absent since Phase 3 opened, and **no job in this repository has ever started the application with `ENVIRONMENT != dev`** — so the two `Settings` guardrails that refuse a dev auth bypass and a default sidecar token outside development have never once fired against a real boot. Until the production-settings work in this release, `environment` was an unvalidated `str`, which meant `"prod"`, `"prd"` and `"Production"` all silently satisfied every `!= "dev"` check.

That is the gap this ADR closes. It is not a hosting-preference question; it is a set of platform constraints meeting a set of code facts that were written for a machine where everything shares a filesystem and a network namespace. Four of those code facts do the deciding:

- **Migration `0001` creates `admin_user` and `migrator` with `BYPASSRLS`.** That statement needs a true Postgres superuser. Any platform whose managed Postgres withholds superuser cannot run this project's first migration.
- **The API refuses to boot without pgBouncer's admin console**, and asserts `pool_mode = transaction` there (`src/serving/startup_checks.py`). ADR 0008 depends on that: session-mode pooling would preserve `SET LOCAL app.tenant_id` across transactions, which *is* the cross-tenant leakage class. No managed pooler on any of the candidate platforms exposes that console to us, so the pooler is our own service or the check is weakened.
- **The serving bundle and the Feast registry are files on disk that two sidecars read once, in `lifespan`.** In Compose they arrive through a shared named volume. Railway volumes are one-per-service and not shareable, so the shared-volume shape has no direct translation.
- **Keycloak's JVM cold start is 8–15 s** (ADR 0007), and the model-server pays a per-worker Feast + LightGBM warm-up before it can serve a learned ranking. Any platform that suspends idle machines makes both of those a user-visible defect rather than a startup cost.

The criteria the choice is made against, in the order they eliminate options:

- **(a) Can it run migration `0001`?** Superuser, or the isolation ADR has to be amended to fit the platform.
- **(b) Does the public/private split survive?** Two services need a public hostname. Seven must not have one, and one of those seven has no authentication at all.
- **(c) How do the serving bundle and the Feast registry reach two separate processes?** In Compose this is a shared volume; on a PaaS it is a design decision with a boot-time failure mode.
- **(d) What do a rollback and a restore actually look like?** Not whether they are possible — what the command is, who runs it at 02:00, and what it takes with it when it runs.
- **(e) What does it cost one person to operate?** Not the monthly bill: the patching, the backup verification, the disk-growth watching, and the number of unknowns that get introduced simultaneously by the first deployment.

## Decision

**Production is Railway, one `production` environment, two custom domains, and the topology below.** Nine long-lived services — `postgres-app`, `postgres-keycloak`, `redis`, `pgbouncer`, `keycloak`, `api`, `model-server`, `feature-server`, `web` — plus five run-to-completion jobs: `release` (schema, seed, preflight), `keycloak-provision` (realms and accounts, manual), `verify` (the post-deploy matrix, nightly cron), `backup` (encrypted off-provider dumps, nightly cron) and `loadcheck` (the k6 canary, manual). Four volumes: `postgres-app` 5 GB, `postgres-keycloak` 1 GB, `redis` 1 GB, and deliberately none on either sidecar. Two public hostnames and only two: `app.<domain>` (`web`) and `auth.<domain>` (`keycloak`).

**`api`, `model-server`, `feature-server`, `pgbouncer`, `redis` and both Postgres services never get a domain and never get a TCP proxy outside a time-boxed maintenance window.** This is not a habit; it is asserted by the deploy workflow before it deploys anything, because `feature-server` has no authentication of any kind and the model sidecar's `/healthz` is unauthenticated. Post-deploy verification therefore runs from a private `verify` service on the same network rather than from a GitHub runner, which is what makes "the API is private" affordable rather than a thing we quietly give up the first time we need to check something.

The release order is part of the decision, not an implementation detail, because several steps fail closed against each other:

1. `keycloak` — the identity store comes up first; its healthcheck deliberately probes the `master` realm's discovery document, because on a first deploy the `demo` realm does not exist yet and probing a not-yet-created realm would deadlock the first deploy forever.
2. `keycloak-provision` (manual, idempotent) — creates both realms, both clients, the audience mapper, and exactly three accounts. Provisioning a tenant means creating a realm **and** a `public.tenants` row; either alone fails closed.
3. `release` — preflight (including an issuer-equality assertion against the public discovery document), then schema, then seed.
4. `model-server` — pre-deploy materializes the online store, then the process warms every worker inside `lifespan` before it becomes healthy.
5. `feature-server`, then `api`, then `web` — the API cannot become ready until the serving realm's JWKS is fetchable and the schema exists, which is why it comes after both.
6. `verify` — the full post-deploy matrix, ending in a sentinel line the workflow greps for.

Config lives in git as one `infra/railway/<service>.json` per service — Railway reads that path relative to the repo root regardless of a service's Root Directory, so twelve small declarative files replace twelve dashboard forms. Auto-deploy is off on every service; the release workflow is the only deploy path, because the per-deploy ordering (`release` → `model-server` → `feature-server` → `api` → `web` → `verify`, steps 3–6 above without the one-time identity steps) is the entire reason the sequence works.

## Rationale

1. **Railway's `postgres` role is a real superuser, and that is the bar.** `CREATE ROLE … BYPASSRLS` is the first statement of the first migration. It is not incidental — `admin_user` is the role the feature sidecars and materialization use to read across tenants, and `migrator` needs to beat `FORCE ROW LEVEL SECURITY` while it backfills. A platform that cannot grant those roles does not run this codebase without an ADR 0008 amendment, and amending the isolation ADR to fit a hosting bill is the wrong direction of travel.

2. **The private mesh makes "the API is private" a real boundary rather than an aspiration.** Every service resolves every other at `<service>.railway.internal` over an encrypted WireGuard mesh with nothing published by default. The public surface is exactly the two hostnames we attach on purpose. That shape is what lets `feature-server` keep having no auth without that being a vulnerability, and it is what makes the `no_public_sidecar` assertion cheap enough to run on every deploy.

3. **The shared-volume problem dissolves rather than being worked around.** The serving bundle is 247 KB and the Feast registry 4 KB, and both are a pure function of a committed fixture with a fixed epoch and a frozen catalog snapshot — there is no wall clock in the seeded data. So the artifact is a build input, not runtime state: it is committed at `infra/model-bundle/` and baked into the sidecar image. `ServingArtifactBundle.load` already re-hashes both files against the manifest's SHA-256 on every boot, so the integrity check lands on the far side of the copy. The payoff is the one that matters at 02:00 — **rolling back the model is rolling back the image**, with no second artifact store to reason about.

4. **Deploy-time healthchecks plus run-to-completion jobs match the lifecycle we actually have.** The real sequence is schema-job → seed-job → materialize → recreate sidecars → serve, and Compose only ever expressed the first hop. Railway's pre-deploy command (separate container, private network, service variables, non-zero exit aborts the deploy) is where `materialize` belongs, and its `restartPolicyType: NEVER` services are where the release, provisioning, verification and backup jobs belong. Every job prints a sentinel final line and the workflow greps for it, because a process that exits cleanly can present in the UI as a stopped deployment.

5. **Config-as-code and exactly one deploy path.** Twelve `infra/railway/*.json` files put build source, start command, healthcheck path, pre-deploy command, restart policy and cron schedule under review alongside the code they configure, which is the only way a dashboard-configured platform stays reviewable. Auto-deploy stays off everywhere so the ordering is never decided by whichever service's watch pattern happened to match a commit; `watchPatterns` are declared anyway, so re-enabling one later is a one-line change rather than an archaeology exercise.

6. **Cost is not the deciding factor, but it is not nothing.** Measured idle RSS across the nine long-lived services is ≈2.0 GB, which at Railway's usage pricing is ≈$27/month all-in including volumes and egress. The alternative that survives longest on technical grounds (a self-managed Droplet) is ≈$58/month before any of the operational work it adds. The crossover is named below so this is revisitable with a number rather than a feeling.

## Alternatives considered

- **DigitalOcean Droplet + Coolify, running the compose files more or less as they are.** The most attractive option on paper: our own Compose files are the deployment artifact, shared volumes keep working, there is no per-service billing to reason about, and an 8 GB / 4 vCPU Droplet at $48/mo plus ~$9.60 for backups is a flat, predictable bill. It falls on a specific fact rather than a general preference: DigitalOcean Managed Postgres's `doadmin` is **not** a superuser, so it cannot execute migration `0001`'s `CREATE ROLE … BYPASSRLS`. The DO path therefore means self-hosting Postgres in a container on the Droplet, which pulls backup, patching, restore-testing and disk-growth management back onto us — the exact operational surface a managed data store exists to remove — and it does so for the *identity* database as well. Against a ≈2 GB steady footprint the flat rate is also poor value today. The honest crossover: **past roughly 6 GB steady RSS the Droplet's flat rate overtakes per-GB billing**, and that is the number that should reopen this decision, not the aesthetics of running our own box.

- **Fly.io.** Genuinely good at the shape of this app — private networking, per-service processes, volumes, a reasonable CLI. Rejected on suspend semantics. Fly machines suspend aggressively when idle, and the two things this system is worst at are exactly the two things a suspend/resume platform amplifies: Keycloak's 8–15 s JVM cold start (which the web app's OIDC discovery trips over) and the model-server's per-worker warm-up, whose absence is precisely the defect that produced HTTP 200 responses with `learned: false` and `fallback_reason="model-server-unavailable"` against a 0.5 s client timeout. We fix that defect by warming inside `lifespan`, which means every worker pays the cost *before* it is reachable — a platform that suspends the worker and resumes it cold re-introduces the defect after every idle period, and the fix is to disable the feature we would be paying for.

- **Managed Kubernetes (GKE/EKS/DOKS).** The correct answer at the far end of this project's phase plan, and CLAUDE.md already keeps k3s/kind as optional after Phase 4. Rejected as disproportionate now: nine long-lived processes with one owner do not need a control plane, a service mesh, an ingress controller and a secrets operator, and on the major clouds the managed control-plane fee alone is comparable to this whole Railway bill before a single node is billed. The learning is real but it is Phase 4+ learning, and doing it now would mean the first production deployment of this system is also the first Kubernetes deployment — two unknowns at once, on the layer where a mistake is a cross-tenant incident.

- **One Railway Postgres instance shared by the application and Keycloak, saving one service.** Tempting at ~$1.35/mo of volume. Rejected on restore granularity: **a Railway volume restore mounts a new volume for the whole service**, so a single instance makes an application-data restore an unannounced identity rollback — every session, every credential change and every realm edit since the snapshot, gone as a side effect of fixing something else. ADR 0007 already preferred separate lifecycles for the identity store; Railway's backup granularity turns that preference into a requirement. Two instances also mean the app's restore drill can be rehearsed without touching identity at all, which is what makes the drill something we are willing to run.

- **Object storage (R2/S3) for the serving bundle and the Feast registry, fetched at boot.** The conventional answer, and the right one when artifacts are produced by a training pipeline on a schedule. Rejected for 247 KB of files that are a deterministic function of a committed fixture: it adds a provider, a credential on two serving containers, an egress path, a fetch-and-verify code path on the critical boot path, and a lifecycle policy — five new failure modes to remove a `COPY` instruction. It also breaks the property we most want, that image rollback and model rollback are the same action. Revisit at Phase 4, when Prefect retraining makes the artifact stop being a repo-determined build product; at that point the manifest should also gain the MLflow run id it currently lacks.

- **Deploy nothing; keep proving the system on the Compose stack.** Worth stating because it is the status quo and it is not absurd: the gates are real, the evidence is real, and a recorded walkthrough costs nothing to run. It is rejected because the specific engineering this project exists to practise is the part Compose cannot reach — a real issuer over TLS behind a proxy, secrets that are not fixtures, a pooler doing SCRAM instead of `trust`, an ordered multi-service release with a rollback target recorded before it starts, a restore drill with an exit code, and the first boot this codebase has ever had with `ENVIRONMENT != dev`. Every one of those is a class of bug that only appears in production shape, and leaving them unexercised is the gap a senior reviewer would find first.

## Sub-decisions recorded here

- **The API is private, and verification runs from inside the network.** The obvious alternative — give `api` a domain so the smoke, reliability and isolation harnesses can run from GitHub Actions — would put an authenticated ML API on the public internet in the same release that first turns `ENVIRONMENT=production` on, and it would tempt the same treatment for `feature-server`, which has no authentication at all. Instead the harnesses were made remote-executable and run as a private `verify` job on the same mesh: realm, client id, client secret, grant type, username and password are all parameters now, so the same code proves the deployment that proves the demo stack. The cost is that a failing check is read from a deployment log rather than a runner's console, which the deploy workflow handles by grepping for the job's sentinel line.

- **The serving bundle and the Feast registry are baked into the image.** Covered in rationale 3; recorded here as a decision because it is the one that most changes how a release feels. There is no artifact fetch on the boot path, no credential for an artifact store on a serving container, and no training code in any deployed image — the sidecar image contains the bundle it will serve and re-hashes it on load. The counterpart obligation is a CI gate that rebuilds the bundle from the committed fixture and fails if it differs from the committed manifest, because a baked artifact nobody can reproduce is worse than a fetched one.

- **`/readyz` becomes a second unauthenticated path.** Non-negotiable #10 names `/healthz` specifically and forbids "internal" unauthenticated paths, so widening it is recorded rather than quietly done. The forcing fact: Railway's deploy probe carries no `Authorization` header and arrives with `Host: healthcheck.railway.app`, so an authenticated readiness path means every deploy fails its healthcheck and **no deployment ever promotes** — there is no partial version of this failure. The test the endpoint is held to is what it can tell an anonymous caller: `/readyz` reports whether this process can reach its own database through the pooler and whether it can fetch the serving realm's JWKS, plus a non-gating `ok`/`unavailable` for the two sidecars. No tenant id, no user data, no model version, no counts — nothing an attacker could not learn by watching the service fail. It answers on a service with no public domain and no TCP proxy, which is asserted on every deploy. The rule's intent is that no *product* surface is exempt from auth; a deploy probe on a private service is not a product surface. The set itself is one `UNAUTHENTICATED_PATHS` frozenset in `src/auth/middleware.py`, read by both the middleware and the OpenAPI security annotations, so it cannot grow in one place only.

- **`/metrics` is deliberately not added in this release.** Prometheus scraping is the obvious next unauthenticated path and it is exactly the one CLAUDE.md forbids in those words, because a scrape endpoint carries per-tenant request counts and latencies. There is no authentication story for a scraper yet and inventing one under deployment pressure is how a third exemption becomes permanent. Phase 5 adds it behind a bearer token or on a second bound port that is never routed publicly, alongside the Grafana work that gives it a consumer.

- **Postgres traffic stays on the private mesh, and TLS to Postgres is not required in code.** Every DSN in `src/config.py` (`database_url`, `app_user_database_url`, `admin_user_database_url`) is built by f-string concatenation with no query-parameter hook, and Feast's `feature_store.yaml` hardcodes `sslmode: disable`. Requiring TLS everywhere today therefore means editing DSN construction *and* the Feast config *and* proving nothing else parses those strings — a code change in the credential path, shipped in the same release as the first production boot. The decision: all Postgres traffic rides Railway's encrypted WireGuard private mesh, no data-store service is given a domain or a TCP proxy, and pgBouncer's `server_tls_sslmode = prefer` gives the `app_user` leg opportunistic TLS for free. This is written down rather than left implicit because it is the one place where "encrypted in transit" rests on the provider's network rather than on our own configuration, and it stops being true the instant someone enables a TCP proxy to debug something. If we ever leave the mesh — a second region, an external analytics consumer, a managed Postgres elsewhere — a `sslmode=require` DSN parameter and a Feast config change are prerequisites of that move, not follow-up work.

- **pgBouncer ships as our own service.** The alternative was to weaken the boot check so the API could talk to Postgres directly. That check is the runtime enforcement of ADR 0008's transaction-pooling requirement, and the failure it prevents is the highest-severity bug class in the project. Running our own pooler costs one 16 MB container and gives us the admin console the check needs, `scram-sha-256` in place of the dev config's `trust`, and a rotation story for the application role passwords. The cost is honest and stated under Risks: the API cannot boot without it.

- **Additive migrations only in production.** Alembic downgrades are untested here, and `0010`'s backfill and `0012`'s audit columns are not safely reversible against live data. Pre-deploy commands run on *every* deploy including a rollback, and `alembic upgrade head` from an older image against a newer database raises "Can't locate revision" — turning one incident into two. So the release bootstrap compares the database's revision against the revisions its own image knows about and **exits 0 when the database is ahead**, and a release that must ship a destructive migration has a database restore as its rollback path, not a redeploy, and a rehearsed restore before it merges.

- **The two-tier latency framing.** `synthetic/load/thresholds.js` remains the SLO's **only** authority: four lines, in CI, at 55 arrivals/s, with ADR 0010's measurement-validity rule, its CPU-steal join and its evidence tree. The production canary is a different and deliberately lower-authority instrument at ~5 arrivals/s: correctness thresholds and the warm-traffic `serving_policy.learned` assertion are **enforced**, p99 is **recorded with no verdict**, and there is no cgroup evidence and no steal join, so it cannot and does not claim ADR 0010's rule. A regression there opens an investigation and a CI re-run; it never re-baselines anything and it never relaxes a threshold.

## Consequences

- **The public surface is two hostnames, and verification moved inside.** Post-deploy checks run from a private `verify` job as a dedicated confidential Keycloak client (`movielens-verify`) with its own account, rather than from a GitHub runner holding production database credentials. `movielens-api` keeps neither `directAccessGrants` nor `serviceAccounts` in production, so the client the browser uses has no password-grant path at all.
- **Personas reset to seed state on every release.** The seeder is idempotent by delete-then-insert over nine known user ids in tenant `demo`, which is what makes the smoke assertions deterministic — and also means any movie state a visitor created on the four personas is wiped by the next deploy. For a portfolio surface that is the right trade, but it is user-visible and belongs on the sign-in door, not only in a runbook.
- **`feature_store.*` grows one generation per release and nothing prunes it.** Materialization appends frames with a wall-clock `event_timestamp`, and `user_item_features` is a users × movies cross join. At 120 titles this is small; it is also unbounded, and the retention rule (delete-then-insert per `as_of`, keeping the last three generations) is an owner decision recorded in the runbook rather than something the code enforces today.
- **Realm changes made in the console or by kcadm must be exported back into git**, or the templates under `infra/keycloak/realms/prod/` drift from reality permanently. `--import-realm` deliberately is not used: it never overwrites a realm that already exists, so editing the JSON after first boot would have no effect while looking like it did.
- **Rotating `MODEL_SERVER_AUTH_TOKEN` on one service and not the other degrades every recommendation to popularity at HTTP 200**, not to an error. The coordinator treats a sidecar rejection as unavailability and falls back. Rotate it in a window, and let `verify`'s learned-path assertion be what confirms recovery.
- **One serving tenant.** The model sidecar is pinned to `manifest.tenant_id` and 403s any other, so a second serving tenant needs a second sidecar process. `demo` serves the product; `default` exists so the isolation canary has a subject that must be denied everywhere.
- **Roughly sixteen generated secrets now exist and need a custody owner.** Every credential in the tree today is a dev fixture — `app_user/app_user`, `admin_user/admin_user`, `migrator/migrator`, `pgbouncer_admin/pgbouncer_admin`, Keycloak `admin/admin`, `movielens-api-secret-dev-only`, `dev-model-server-token` and the rest — and the repository is public, so every one of them has a replacement to generate, a home to live in and a rotation story. CI holds zero GitHub secrets today, so the deploy workflow's `production` environment is new plumbing rather than an extension of existing plumbing. The generation rule is not cosmetic: DSNs are f-string-concatenated with no URL-encoding, so a password containing `@` mis-parses the host and one containing `%` is percent-decoded.
- **Non-negotiables #2, #4 and #11 keep CI as their only authority.** Feature parity has no remote-executable form and pointing the CI suite at production would mean handing a runner production database and Redis credentials and letting it write demo data. The pinned load gate needs Compose recreation, `docker stats`, cgroup reads and a `/proc/stat` probe, none of which have a remote form. Deploying does not weaken those gates and does not extend them either; the deployment adds the canary and the nightly matrix, and says plainly that they are weaker instruments.
- **Non-negotiable #5 gains its first mechanical form.** `make train` now exists as a fixed-seed, fixed-`--as-of` build, and `make serving-artifacts-check` rebuilds the bundle and compares it against the committed manifest — so "the same seed produces the same artifact" is a gate rather than a claim. It is a build-time property; the runtime evidence is the sidecar re-hashing the bundle on load.
- **The dev Compose stack is unchanged and stays the development surface.** Production shape is expressed by a separate `docker-compose.prod.yml` rehearsal stack and the Railway config files; `docker-compose.yml` keeps its trust-auth Postgres, its `trust` pooler and its `start-dev` Keycloak, because a development stack that needs generated secrets to boot is a development stack nobody uses. The obligation that creates is that production shape must be rehearsed somewhere, which is what the rehearsal stack is for.
- **Healthchecks are deploy-time only.** Railway polls the healthcheck path until it returns 200, swaps the deployment in, and then stops checking. There is no continuous liveness signal from the platform, so the nightly `verify` cron and a scheduled canary workflow are the only recurring health signals the deployment has — which is also what finally gives ADR 0010's "nightly" enforcement tier a real trigger rather than an intention.
- **Audit coverage is recommendations-only in production too.** `src/serving/audit.py` matches `^/users/(\d+)/recommendations/?$`, so every mutation passes through unaudited. Deploying does not change that, and the runbook says so plainly rather than letting CLAUDE.md's "every authenticated request emits a row" read as a description of what is running.

## Risks

- **A typed setting entered as a variable-panel string crash-loops the container.** `keycloak_authorized_parties` is a `tuple[str, ...]`, which pydantic-settings parses as JSON — the comma-separated form a variable panel invites raises `SettingsError` on construction, and every container that builds `Settings()` fails identically with no partial mode. Mitigation: the release preflight asserts the parsed value is a list of at least one entry *before* the API ever boots on it, and the runbook prints the JSON form in bold.
- **Shared CPU with no steal visibility.** ADR 0010's measurement-validity rule depends on reading the host's CPU-steal record; on Railway there is no such record and no cgroup access. Mitigation: the canary records p99 without a verdict, CI keeps the verdict, and a persistent production/CI gap is treated as an investigation trigger, not as a reason to re-baseline.
- **The Keycloak admin console is internet-reachable at `https://auth.<domain>/admin`.** A Railway domain has no path-level ACL, so this exposure is structural rather than a setting we forgot. Mitigation: a 48-character generated bootstrap password used exactly once, a named human admin, brute-force protection on both realms, `registrationAllowed: false`, and deletion of the bootstrap variables plus disabling of the bootstrap account immediately after provisioning. Fronting both hostnames with a CDN path rule is the stronger form and remains available.
- **Single-provider concentration.** Compute, both databases, Redis and the volumes are one account. Mitigation: nightly `pg_dump` of both databases, encrypted client-side with `age` and copied to an off-provider object store, with a restore drill that has an exit code rather than a paragraph — because backups at the same provider as the data are one account suspension away from total loss.
- **pgBouncer is a single point of failure the API refuses to boot without.** By construction: the boot check that proves transaction pooling is also a hard dependency on the pooler being up. A pgBouncer outage is a full API outage even though Postgres is healthy. Accepted, because the alternative is an API that can boot into a configuration where `SET LOCAL app.tenant_id` leaks across requests.
- **Any signed-in `demo`-realm account can read and mutate all four personas.** Persona access is gated by the `demo-impersonator` realm role and there is no `/me` subject-to-profile ownership mapping yet (ADR 0012 names it as future work), so on a public URL the blast radius of one account is the whole demo tenant's product surface. Mitigation: registration disabled, exactly three deliberately-created accounts (`walkthrough`, `verify`, `isolation`), the `isolation` account deliberately *without* the role so the canary has a subject that must be denied, and a line on the sign-in door stating that the published account drives shared named personas. The real fix is `/me` ownership, which stays a product-track item.
- **The pre-deploy command runs on every deploy, including rollbacks.** A pre-deploy that assumes it is always moving forward is a rollback that fails at the worst moment. Mitigation: the schema step is a no-op when the database is ahead of the image, the additive-only policy above keeps that no-op safe, and a rollback across a destructive migration is explicitly a restore rather than a redeploy.
- **First-deploy ordering is circular if any step is skipped.** The API cannot become ready until the `demo` realm exists *and* migrations have run; the model sidecar refuses to boot against an unmaterialized Redis. Mitigation: the order is `keycloak` → `keycloak-provision` → `release` → sidecars → `api` → `web`, the release preflight asserts issuer equality before anything else runs, and a crash-looping sidecar reporting a missing feature event time means "materialize", not "roll back".

## How we'd know we're wrong

- **Production p99 sits persistently above the CI figure at the canary's ~5 arrivals/s.** At 1/11th the CI rate the two should not be comparable in the direction that matters; if production is slower on a nearly idle service, the platform's shared CPU is the suspect and the answer is either dedicated capacity or a different provider — not a threshold change.
- **Steady RSS approaches ~6 GB.** That is the arithmetic crossover where a flat-rate Droplet becomes cheaper than per-GB billing, and it would also mean the deployment has stopped being the small portfolio system this ADR sized for.
- **A second serving tenant becomes necessary.** The one-tenant-per-sidecar pin makes that a second process per tenant, which does not scale past a handful. It would mean the tenant-aware routing work Phase 6 owns has arrived early, and that the sidecar needs a multi-bundle registry rather than a single baked manifest.
- **More than one incident traces to the baked-artifact model rather than to data.** Baking trades flexibility for a rollback story; if we find ourselves rebuilding images to change a model rather than fixing data, the object-storage alternative above is the upgrade and Phase 4's retraining pipeline is its natural trigger.
- **`verify` goes green while the product is visibly broken.** The matrix asserts persona slugs, policies, the learned flag, the auth boundary, isolation denials, a write round trip and the audit rollup. If a real regression walks past all of that, the matrix is under-specified and the fix is a new row — this is the check we would most like to be told is insufficient, and a browser canary that only signs in and loads two routes is a thin backstop for it.
- **Any deploy is fixed by hand and the fix is not immediately written into a job.** Anything done by hand at 02:00 that is not captured becomes the next incident. That failure mode is the one this ADR is least able to see coming, which is why the runbook records the manual steps that remain and why the restore drill records everything done outside the script.
